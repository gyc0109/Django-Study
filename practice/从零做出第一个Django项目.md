## 第 0 章　先有想法，再有代码

### 0.1 从一个真实的困扰开始

先别打开终端。先想一件事。

你每天要学的东西很多：Django 看到第几章了、Redis 缓存那个坑还没复现、前端那个代理配置还没试。**记在脑子里，两天就忘了；记在手机备忘录，翻起来又太麻烦。**

于是你冒出一个念头：

> 「我要不自己做一个待办清单？就给自己用。」

这个念头，就是一个项目的起点。

注意：**绝大多数教程是从「打开终端，输入 django-admin」开始的。那是错的。** 那一刻你还不知道自己要做的是一个什么东西。先想清楚，再动手。

### 0.2 拿出纸，回答四个问题

不用写代码。就回答下面四个问题，能答上来，项目就成立了一半。

#### 问题一：谁用？

只有你自己。

这个答案看起来没用，其实决定了后面很多东西：

- 不需要注册登录（省掉一大块）
- 不需要权限管理（省掉一大块）
- 不需要做得好看（第一版甚至可以不写 CSS）
- 不需要考虑并发（一个人用，不会有两个人同时改同一条）

**每砍掉一个「不需要」，你就少踩十个坑。**

#### 问题二：记什么？

一条待办，需要记住哪些信息？

你先自己写一遍，再对照我下面这份：

| 信息 | 例子 | 为什么需要 |
| --- | --- | --- |
| 内容 | 把 Redis 缓存的坑复现一次 | 不写内容就不知道要做什么 |
| 是否完成 | 未完成 / 已完成 | 待办清单的核心就是「勾掉」 |
| 创建时间 | 2026-11-08 20:15 | 后来想按时间排序、想知道拖了多久 |

再想想，还有什么？

- 优先级（高/中/低）？——第一版不需要。真需要了再加一个字段，成本很低。
- 截止日期？——同上，先不做。
- 分类？——那是图书管理项目的「分类」，这里先不引入。

**这一步的产出，就是后面的「数据库表结构」。** 你现在画的三行，很快就会变成 `models.py` 里的三个字段。

#### 问题三：怎么用？

把「你会对它做的动作」列出来：

| 动作 | 用一句话描述 | 第一版做不做 |
| --- | --- | --- |
| 新增 | 想到一件事，记下来 | 做 |
| 查看 | 打开页面看到所有待办 | 做 |
| 勾选完成 | 做完了，打个勾 | 做 |
| 删除 | 记错了，删掉 | 做 |
| 编辑文字 | 内容写错一个字，改一下 | **不做** |
| 排序 | 按时间/状态排 | **不做** |
| 搜索 | 待办太多，搜关键词 | **不做** |

**看到那个「不做」栏了吗？这是本章最重要的一列。**

新手做项目最常见的死法，不是不会写，是**什么都想做**。结果每一块都做了个半成品，没有一块能用，最后放弃。

第一版只做四个动作。做完、跑通、能天天用，再谈别的。这个思路叫 **MVP（最小可用版本）**。

#### 问题四：什么时候算成功？

给自己定一个**能用一句话验证**的标准：

> 「我打开浏览器，能记一条待办、能看到列表、能勾掉它，并且关掉再打开数据还在。」

注意最后半句「关掉再打开数据还在」——这要求数据存进数据库，而不是存在内存里。一开始就把标准定死，后面才不会自欺欺人。

### 0.3 把想法翻译成两张表

现在把前面两个问题的答案并排放：

```text
名词（记什么）              动词（怎么用）
─────────────              ─────────────
一条待办                    新增
  ├─ 内容                   查看列表
  ├─ 是否完成               勾选完成
  └─ 创建时间               删除
```

这两列，对应的就是 Web 开发里最核心的两样东西：

| 你写的 | 计算机里的名字 | Django 里叫什么 |
| --- | --- | --- |
| 名词（一条待办有哪些信息） | 数据模型 / 表结构 | Model（模型） |
| 动词（能对它做什么） | 接口 / API | View（视图） |

**记住这句话，整个项目都靠它：**

> **名词决定表结构，动词决定接口。**

你现在还没有写一行代码，但你已经完成了这个项目 60% 的设计。剩下的，只是把它们翻译成 Python。

### 0.4 第一版长什么样

不用画图软件，用文字画就行：

```text
┌────────────────────────────────────────┐
│  我的待办                               │
├────────────────────────────────────────┤
│  [ 输入框：今天要做什么？      ] [添加]  │
├────────────────────────────────────────┤
│  ☐  把 Redis 缓存的坑复现一次     [删除] │
│  ☑  看完 Django 第 5 章           [删除] │
│  ☐  试一下 Vite 的 proxy 配置      [删除] │
└────────────────────────────────────────┘
```

一个输入框、一个按钮、一个列表。就这么多。

你在第 8 章做出来的前端，会长得非常像这张图。现在先在脑子里有个画面。

### 0.5 本章复盘

**你现在拥有的：**

- 一个一句话说清楚的项目：「给自己用的待办清单」
- 3 个字段（内容、是否完成、创建时间）
- 4 个动作（新增、查看、勾选、删除）
- 1 条验收标准（关掉再打开，数据还在）

**你现在应该能回答：**

- 为什么不先做「编辑」和「搜索」？

- 「名词决定表结构，动词决定接口」是什么意思？

## 第 1 章　选型：为什么是 Django

### 1.1 先比较三个方案

你要一个待办清单，其实有三条路：

| 方案 | 怎么做 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 用现成工具 | Excel、飞书表格、手机自带备忘录 | 十分钟就能用 | 学不到东西 |
| B. 用现成 App | 应用商店搜「待办」 | 功能比自己做的强十倍 | 学不到东西 |
| C. 自己写 | 就是本文要做的 | 能学到东西，而且完全按自己想法来 | 要花时间 |

**你现在的问题不是「怎么最快记下待办」，而是「怎么学会做一个项目」。** 所以选 C。

这个判断很重要：**目标不同，最优解就不同。** 如果只是记事，别写代码，用备忘录。写代码是因为你想学写代码。

### 1.2 为什么是 Django，不是 Flask / FastAPI

同样是自己写，Python 里还有别的选择。

| 框架 | 它给你什么 | 适合谁 |
| --- | --- | --- |
| Flask | 一个路由 + 模板，其它自己装 | 想要极简、完全掌控的人 |
| FastAPI | 现代异步、自动生成接口文档 | 主要写 JSON 接口、不想要后台界面的人 |
| **Django** | ORM + 迁移 + Admin 后台 + 模板 + 表单，一整套 | **想一个框架走完全流程的人** |

选 Django 的三个具体理由：

**理由一：它会替你管数据库。**

你只写 Python 类：

```python
class Todo(models.Model):
    content = models.CharField(max_length=200)
```

Django 就会去 MySQL / SQLite 里建表、建字段。你几乎不用写 SQL。这个能力叫 **ORM**。

**理由二：它会给你一个现成的管理后台。**

只要注册一下模型，你就有了一个能增删改查的网页后台——**不用写一行前端代码**。

这对新手意义巨大：你可以在第 4 章就拥有一个能录入数据的界面，而不必等到第 8 章写完 Vue。

**理由三：它自带「数据库版本管理」。**

你改了模型字段，它帮你生成迁移文件、帮你执行，还能回滚。这个东西叫 **migrations**。

后面你会发现，这是 Django 最值钱的部分之一。

> 一句话总结：**Flask 给你一块地，Django 给你一套毛坯房。**

### 1.3 两个「先不做」的决定

选完框架，还有两个选择要做。这两个决定，比选框架更能决定你这次学得顺不顺。

#### 决定一：第一版用 SQLite，不用 MySQL

你可能想：我都装好 MySQL 了，为什么不用？

因为**你现在最不需要的就是多一个变量**。

| | SQLite | MySQL |
| --- | --- | --- |
| 要不要装 | 不用，Python 自带 | 要装、要起容器、要建库、要建账号 |
| 要不要配连接 | 不用，Django 默认就是它 | 要配 HOST/PORT/USER/PASSWORD |
| 数据存哪 | 项目里一个 `db.sqlite3` 文件 | 一个独立服务 |

新手同时面对「Django 不熟 + MySQL 连不上」两个问题，报错时根本分不清是谁的错。

**先用 SQLite 把整个项目跑通**，等业务逻辑都对了，再换 MySQL——那时候如果连不上，你就能确定 100% 是数据库配置的问题，而不是代码的问题。

这个方法叫 **控制变量**。它不只适用于编程。

#### 决定二：第一版不写 Vue，先用 Django 自带模板

同样的道理。一个请求从浏览器发出，要经过：

```text
浏览器 → Vue 组件 → axios → 代理 → Django 路由 → 视图 → 数据库
```

这条链上任何一环错了，页面都是白屏。你现在还没能力快速定位是哪一环。

所以第一版把链条缩短：

```text
浏览器 → Django 路由 → 视图 → 模板 → HTML
```

少了两环，出问题一眼就能看出来。

第 8 章我们再接 Vue。那时候你对 Django 已经熟了，加上前端也只是多两环，不会慌。

### 1.4 准备 Python 环境

现在终于可以动手了。

#### 第一步：确认 Python 版本

Django 4.2 官方支持 **Python 3.8 ~ 3.12**。太新的版本（比如 3.13、3.14）可能装得上但会出各种奇怪问题。

先看你机器上有什么：

```bash
python3 --version
```

如果输出是 `Python 3.11.x` 或 `3.12.x`，很好，直接用。

如果输出是 3.13 / 3.14 或者根本没有，用 pyenv 装一个 3.11：

```bash
pyenv install 3.11.13
pyenv versions          # 确认装好了
```

> 已经装过 3.11 的话，`pyenv versions` 里能看到，不用重复安装。

#### 第二步：建项目目录

```bash
cd ~/Labs
mkdir todo_lab
cd todo_lab
```

现在这个目录是**空的**。记住这一刻——这是你整个项目真正的起点。

#### 第三步：指定 Python 版本

如果你用 pyenv：

```bash
pyenv local 3.11.13
python --version
```

**你现在应该看到：**

```text
Python 3.11.13
```

如果看到的还是 3.14，说明 `pyenv local` 没生效，检查一下 `pyenv init` 有没有写进你的 `~/.zshrc`。

#### 第四步：创建虚拟环境

```bash
python -m venv .venv
source .venv/bin/activate
```

**虚拟环境是什么？** 一句话：给这个项目单独准备一个「Python 包仓库」。

不用虚拟环境会怎样？你机器上所有项目共用一个 Python，A 项目要 Django 3.2，B 项目要 Django 4.2，装一个就会把另一个搞坏。虚拟环境让每个项目互不干扰。

激活后，你的终端提示符前面会多出 `(.venv)`：

```text
(.venv) ➜  todo_lab
```

**看到 `(.venv)` 才算激活成功。** 后面所有命令都必须在这个状态下敲，否则会装到系统 Python 里。

> 每开一个新终端，都要重新 `source .venv/bin/activate`。忘了激活是新手第一大坑，症状是「明明装了 Django，却说找不到」。

#### 第五步：装 Django

```bash
pip install "Django==4.2.30"
```

验证：

```bash
python -c "import django; print(django.get_version())"
```

**你现在应该看到：**

```text
4.2.30
```

## 第 2 章　第一次让它跑起来

### 2.1 一个命令生成项目骨架

确认三件事：

1. 当前在 `~/Labs/todo_lab` 目录
2. 终端提示符前面有 `(.venv)`
3. `python -c "import django"` 不报错

然后敲：

```bash
django-admin startproject config .
```

**注意最后那个点 `.`，它很重要。**

这条命令的意思是：在当前目录下，创建一个叫 `config` 的「项目配置包」。

- 如果**不加** `.`，它会在当前目录下再套一层 `config/`，变成 `todo_lab/config/config/settings.py`，多一层没必要的嵌套。
- **加了** `.`，它把 `manage.py` 放在当前目录，配置包 `config/` 放在旁边。

敲完，看看目录里多了什么：

```bash
ls
```

**你现在应该看到：**

```text
config      manage.py
```

再往里看一层：

```bash
find . -path ./.venv -prune -o -type f -print | sort
```

**你现在应该看到（已经去掉缓存文件）：**

```text
./config/__init__.py
./config/asgi.py
./config/settings.py
./config/urls.py
./config/wsgi.py
./manage.py
```

就 6 个文件。Django 没有偷偷给你生成一堆东西——它很克制。

### 2.2 这 6 个文件分别干什么

不用背，但要知道每个文件「归谁管」，以后改东西才知道去哪改。

| 文件 | 一句话作用 | 你以后会在这里做什么 |
| --- | --- | --- |
| `manage.py` | 命令行入口。所有 `python manage.py xxx` 都靠它 | 基本不改 |
| `config/settings.py` | 全局配置：数据库、时区、装了哪些 app | **改得最多** |
| `config/urls.py` | 总路由表：哪个网址交给谁处理 | 每加一个模块就改一次 |
| `config/wsgi.py` | 给正式部署用的入口 | 现在完全不用管 |
| `config/asgi.py` | 给异步部署用的入口 | 现在完全不用管 |
| `config/__init__.py` | 让 `config` 被当成一个 Python 包 | 现在空的 |

先打开 `config/settings.py` 扫一眼。不用全看懂，找这几行：

```python
INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
]

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.sqlite3",
        "NAME": BASE_DIR / "db.sqlite3",
    }
}
```

**这两块就是接下来所有事情的入口：**

- `INSTALLED_APPS` 告诉你「这个项目装了哪些功能模块」。你写的 `todos` app 以后要加到这里。
- `DATABASES` 告诉你「数据存哪」。看到 `sqlite3` 和 `db.sqlite3` 了吗？这就是 1.3 节那个决定的落地。

### 2.3 第一次 runserver

先别写任何代码，先让它跑起来。

```bash
python manage.py runserver 8002
```

**为什么是 8002，不是默认的 8000？**

因为 8000 很可能被你之前的项目占着（project1 用 8000，practice 用 8001）。端口被占用的报错长这样：

```text
Error: That port is already in use.
```

看到这个不要慌，换个端口号就行。**新手最容易在这里以为「Django 坏了」，其实只是端口撞了。**

敲完，**你现在应该看到：**

```text
Watching for file changes with StatReloader
```

### 2.4 创建 app：为什么 Django 要分 project 和 app

项目骨架有了，但它是空的。接下来要装「业务模块」。

```bash
python manage.py startapp todos
```

**你现在应该看到多了一个 `todos/` 目录：**

```text
todo_lab/
├── manage.py
├── config/
│   ├── __init__.py
│   ├── asgi.py
│   ├── settings.py
│   ├── urls.py
│   └── wsgi.py
└── todos/
    ├── __init__.py
    ├── admin.py
    ├── apps.py
    ├── migrations/
    │   └── __init__.py
    ├── models.py
    ├── tests.py
    └── views.py
```

**project 和 app 到底什么关系？**

用一句话区分：

> **project 是「一整个网站」，app 是「网站里的一个功能模块」。**

一个 project 可以装很多 app。比如你的图书管理项目里，以后可能有 `books`（图书）、`users`（用户）、`orders`（订单）。它们各自独立，互不干扰。

现在的 `todos` 就是「待办」这个功能模块。它的文件分工：

| 文件 | 作用 | 什么时候会改 |
| --- | --- | --- |
| `models.py` | 数据长什么样（表结构） | 第 3 章 |
| `views.py` | 收到请求后干什么（业务逻辑） | 第 2 章就开始改 |
| `admin.py` | 后台怎么展示这个模型 | 第 4 章 |
| `apps.py` | app 自身的配置 | 基本不改 |
| `tests.py` | 自动化测试 | 以后想写测试时 |
| `migrations/` | 数据库变更记录 | 第 3 章自动生成 |

**注意：`startapp` 没有给你生成 `urls.py`。** 需要的话自己建。这是一个常见困惑点——「为什么别人的 app 里有 urls.py，我的没有？」因为那个文件本来就是可选的，Django 不强制。

### 2.5 把 app 注册进项目

刚创建的 app，Django 还不知道它的存在。要手动登记。

打开 `config/settings.py`，找到 `INSTALLED_APPS`，在**末尾**加一行：

```python
INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
    "todos",          # ← 新加的这一行，注意逗号
]
```

**为什么必须写这一行？**

因为 Django 要根据这个列表，去每个 app 里找模型、找管理命令、找模板。没登记，它就像不认识这个目录一样。

**不写会怎样？** 现在还不明显，因为 `todos` 里还没有模型。但第 3 章你一写模型就会发现「迁移没有生成任何东西」——那就是忘了这一步。

> 顺便说一个常见错误：`"todos"` 后面忘了逗号，或者用了中文引号 `“todos”`。Python 报错会指到下一行，看起来莫名其妙。

### 2.6 写第一个视图：一个函数就是一个页面

现在让 `todos` 这个 app 对外提供第一个网址。

#### 第一步：写视图函数

打开 `todos/views.py`，把内容改成：

```python
from django.http import HttpResponse


def hello(request):
    """收到一个请求，返回一句话。"""
    return HttpResponse("你好，待办清单！")
```

三行代码，逐行解释：

- `HttpResponse` 是 Django 给你的「响应」类。你可以把它理解成一个信封，里面装着要返回给浏览器的内容。
- `def hello(request)` 是**视图函数**。Django 收到请求后会调用它，并把请求对象 `request` 传进来。
- `return HttpResponse(...)` 就是往信封里塞一句话，寄回去。

**你现在应该注意到一件事：这里没有「返回一个 HTML 文件」，只返回了一串文字。**

对。视图的本质就是「给一个请求，返回一个响应」。响应里装什么，你说了算。

#### 第二步：给这个函数配一个网址

在 `todos/` 目录下**新建**一个文件 `urls.py`：

```python
from django.urls import path

from . import views

urlpatterns = [
    path("hello/", views.hello, name="hello"),
]
```

- `urlpatterns` 是一个列表，Django 从上往下匹配。
- `path("hello/", ...)` 表示：当网址是 `hello/` 时，交给 `views.hello` 处理。
- `name="hello"` 是给这个网址起个名字，以后可以在代码里反查它。现在用不上，但养成习惯。

**注意结尾的 `/`。** `"hello/"` 和 `"hello"` 在 Django 里行为不一样，后面讲接口时这个坑会咬人。

#### 第三步：把 app 的路由挂到总路由上

现在 `todos/urls.py` 还只是一个孤儿文件，没人调用它。要在 `config/urls.py` 里把它接进来。

打开 `config/urls.py`，改成：

```python
from django.contrib import admin
from django.urls import include, path

urlpatterns = [
    path("admin/", admin.site.urls),
    path("todos/", include("todos.urls")),
]
```

关键在第二行：`include("todos.urls")`。

它的意思是：**所有以 `todos/` 开头的网址，都交给 `todos/urls.py` 里的规则继续匹配。**

于是完整链路变成：

```text
浏览器请求 /todos/hello/
    ↓
config/urls.py 匹配到 "todos/" 前缀
    ↓
把剩下的 "hello/" 交给 todos/urls.py
    ↓
todos/urls.py 匹配到 "hello/"
    ↓
调用 views.hello()
    ↓
返回 "你好，待办清单！"
```

这种「总路由 → 分路由」的结构叫**路由分发**。项目大了以后，每个 app 管自己的网址，互不干扰，非常清晰。

#### 第四步：跑起来看

```bash
python manage.py runserver 8002
```

浏览器访问：

```text
http://127.0.0.1:8002/todos/hello/
```

**你现在应该看到：**

```text
你好，待办清单！
```

不容易。这是你自己写出来的第一个网页。

> 如果访问 `/todos/hello/` 看到的是 404，先检查三件事：
> 1. `todos/urls.py` 里的路径是不是 `"hello/"`（不是 `"/hello/"`，开头不要斜杠）
> 2. `config/urls.py` 里是不是 `include("todos.urls")`
> 3. 有没有重启服务（改了 `settings.py` 或新增文件时，偶尔需要手动重启）

### 2.7 故意犯一次错：学会读报错

这一节不要跳过。**会读报错，比会写代码更重要。**

故意把网址敲错一个字母，访问：

```text
http://127.0.0.1:8002/todos/hell/
```

**你现在应该看到一个黄色页面**（Django 的调试页），大字写着：

```text
Page not found (404)
```

往下翻，你会看到：

- **Request URL**: `/todos/hell/` —— 你请求了什么
- **Using the URLconf defined in config.urls** —— 它去哪张路由表里找的
- **Django tried these URL patterns, in this order** —— 它试了哪些规则
- 下面列出一串 `admin/`、`todos/hello/` —— **这就是它认识的所有网址**

**这个列表极有用。** 当你 404 的时候，先看这个列表：你想访问的网址在不在里面？

- 不在 → 你的路由没写对，或者没被 include 进来
- 在，但访问还是 404 → 可能是方法不对（比如只能用 POST，你用了 GET），或者路径细节不一致（少斜杠、多空格）

同时，回到终端，你也应该看到一行：

```text
Not Found: /todos/hell/
```

现在把网址改回 `hello/`，刷新，恢复正常。

**记住这个感受：404 不可怕，它只是在告诉你「我认识的路里没有这一条」。**
