## 第 0 章 这个项目到底在做什么

### 0.1 一句话介绍

做一个「图书管理」系统：可以在网页上对**分类**和**图书**做增删改查，支持搜索、按分类筛选、分页；点一个按钮，后台异步算出一份库存报表再显示出来。

### 0.2 为什么用「图书管理」当练习

因为它天然包含真实项目里最常见的三件事：

| 真实项目里的问题 | 图书管理里的对应物 |
| --- | --- |
| 两张表有关联（用户-订单、文章-评论） | 分类-图书（一对多） |
| 列表数据多，要搜索、筛选、翻页 | 图书列表 |
| 有个接口很慢（统计报表、导出 Excel） | 生成库存报表 |

把这三点吃透，你换任何业务都能套。

### 0.3 技术栈与它们各自的职责

```
浏览器（Vue 2.7 页面）
      │  HTTP + JSON
      ▼
Vite 开发服务器 :5174  ──代理 /api──▶  Django :8001
                                        │
                        ┌───────────────┼────────────────┐
                        ▼               ▼                ▼
                   MySQL :3307     Redis :6380      Celery worker
                   （存业务数据）   （缓存+队列）    （执行异步任务）
```

| 技术 | 版本 | 它负责什么 | 不用它会怎样 |
| --- | --- | --- | --- |
| Django | 4.2 LTS | Web 框架，处理请求、路由、ORM | 你要自己写 socket、解析 HTTP |
| DRF | 3.17 | 在 Django 上快速写 REST 接口 | 每个接口都要手写 JSON 序列化 |
| MySQL | 8.4 | 持久化存数据 | 重启服务数据就没了 |

| Celery | 5.7 | 后台异步执行耗时任务 | 请求卡住，用户干等 |

| Vite | 5.4 | 前端开发服务器、打包、代理 | 手动刷新、手动处理跨域 |

## 第 1 章 先补 6 个最基础的概念

这一章不写代码，只建立心智模型。看不懂后面会很痛苦，请耐心读完。

### 1.1 前端 / 后端 / 数据库 是什么关系

- **前端**：跑在浏览器里的页面，负责「显示」和「收集用户操作」。
- **后端**：跑在服务器上的程序，负责「校验数据、算逻辑、读写数据库」。
- **数据库**：一个专门存数据的软件，断电也不丢。

前端不能直接连数据库。为什么？

1. 数据库密码会暴露给所有访客；
2. 任何人都能伪造 SQL 删你的数据；
3. 浏览器根本不允许发起 MySQL 协议连接。

所以必须有个「后端」夹在中间做保安。

### 1.2 什么是 API 和 REST

**API** = 前端和后端约定好的「说话方式」。后端说：你访问 `/api/books/`，我就给你图书列表。

**REST** 是一套约定俗成的风格，核心是「用 URL 表示资源，用 HTTP 方法表示动作」：

| 动作 | HTTP 方法 | URL | 含义 |
| --- | --- | --- | --- |
| 查列表 | GET | `/api/books/` | 给我所有书（可分页） |
| 查单条 | GET | `/api/books/3/` | 给我 id=3 的书 |
| 新增 | POST | `/api/books/` | 创建一本新书 |
| 全量改 | PUT | `/api/books/3/` | 用新数据**整体替换** id=3 |
| 局部改 | PATCH | `/api/books/3/` | 只改我传的字段 |
| 删除 | DELETE | `/api/books/3/` | 删掉 id=3 |

记住这张表，Django 后面的 `ModelViewSet` 就是自动帮你实现了这 6 个。

### 1.3 什么是 JSON

前后端之间传数据的格式，长这样：

```json
{
  "id": 1,
  "title": "Python 编程从入门到实践",
  "price": "89.00",
  "stock": 12,
  "category": 1,
  "category_name": "技术"
}
```

注意几点：

- 字符串必须用**双引号**，不能用单引号；
- 最后一个字段后面**不能有逗号**；
- 价格是字符串 `"89.00"` 而不是数字 `89.00` —— 因为后端用了 `DecimalField`（金融计算要精确，浮点数会丢精度）。

### 1.4 状态码：后端用数字告诉你结果

| 状态码 | 含义 | 本项目什么时候出现 |
| --- | --- | --- |
| 200 | 成功 | 查询、修改成功 |
| 201 | 已创建 | 新增成功 |
| 202 | 已接受（稍后处理） | 提交 Celery 任务 |
| 204 | 成功但无内容 | 删除成功 |
| 400 | 你传的数据有问题 | 价格填负数、删有书的分类 |
| 404 | 资源不存在 | 访问 `/api/books/99999/` |
| 500 | 服务器内部崩了 | 代码有 bug |

> 前端判断「成功还是失败」不能只看 `res.data`，要配合状态码。axios 默认在 4xx/5xx 时会走 `catch`，所以我们代码里错误都写在 `catch (err)` 里。

### 1.5 ORM 是什么

**ORM = 用写 Python 类的方式操作数据库**，不手写 SQL。

```python
# 原生 SQL
# SELECT * FROM library_book WHERE price > 50 ORDER BY id DESC LIMIT 5;

# 等价的 ORM
Book.objects.filter(price__gt=50).order_by("-id")[:5]
```

好处：

1. 换数据库（MySQL → PostgreSQL）基本不用改代码；
2. 天然防 SQL 注入（参数会被安全转义）；
3. 有 IDE 补全，字段拼错能提前发现。

代价：ORM 写不好会产生低效查询（第 11 章细讲）。

### 1.6 App 是什么

一个 Django 项目可以包含多个 **app**（应用），每个 app 是一个功能模块。

```
config/    ← 项目级配置（全局，只有一个）
library/   ← 业务模块（图书管理，可以有很多个）
```

类比：`config` 是公司总部（规定制度），`library` 是一个部门（干具体业务）。以后你要加「用户中心」，就再建一个 `accounts` app，互不干扰。

```bash

```


> **为什么不每个项目都新建容器？**
> 一台机器上跑多个 MySQL 实例很浪费内存（一个就 400MB+）。更好的做法是「一个 MySQL 实例，多个数据库」：主项目用 `django_study` 库，练习项目用 `practice_db` 库，物理隔离、逻辑共享。Redis 同理，用「编号不同的库」（0/1 给主项目，2 给缓存，3 给 Celery）。

### 2.2 创建练习用的数据库

MySQL 容器启动时只自动建了 `django_study`，我们要手动建 `practice_db`：

```bash
docker exec -it django-study-mysql mysql -uroot -pHenhaoji@119 -e "
CREATE DATABASE IF NOT EXISTS practice_db
  DEFAULT CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;
GRANT ALL PRIVILEGES ON practice_db.* TO 'django'@'%';
FLUSH PRIVILEGES;
"
```

逐句解释：

| 语句 | 作用 | 为什么需要 |
| --- | --- | --- |
| `CREATE DATABASE ... DEFAULT CHARACTER SET utf8mb4` | 建库并指定字符集 | `utf8mb4` 才能存 emoji 和生僻字；老 `utf8`（3 字节）存不了 |
| `COLLATE utf8mb4_unicode_ci` | 指定排序/比较规则 | `_ci` = case insensitive，比较时忽略大小写 |
| `GRANT ALL PRIVILEGES ON practice_db.*` | 授权给 `django` 用户 | Django 用的是 `django` 账号，不是 root，权限最小化更安全 |
| `FLUSH PRIVILEGES` | 让权限立即生效 | 修改权限表后刷新内存缓存 |

验证（能看到 `practice_db` 就对了）：

```bash
docker exec -it django-study-mysql mysql -uroot -pHenhaoji@119 -e "SHOW DATABASES;"
```

## 第 3 章 从零创建 Django 项目

> 本项目的文件已经写好了。本章的意义是：**如果全删了，你能自己重建出来。** 建议把命令读一遍，理解每条命令生成了什么。

### 3.1 生成项目骨架

```bash
cd /home/gyc/Labs/Django-Study/practice/backend
django-admin startproject config .
```

注意最后那个**点**，很关键：

| 写法 | 生成结果 | 好不好 |
| --- | --- | --- |
| `django-admin startproject config` | `backend/config/config/settings.py`（多套一层） | ❌ 路径啰嗦 |
| `django-admin startproject config .` | `backend/config/settings.py` | ✅ 推荐 |

生成的结构：

```
backend/
├── config/
│   ├── __init__.py
│   ├── settings.py    ← 全局配置
│   ├── urls.py        ← 总路由
│   ├── wsgi.py        ← 同步部署入口
│   └── asgi.py        ← 异步部署入口
└── manage.py          ← 命令行工具
```

> **WSGI / ASGI 是什么？** 是「Web 服务器（Nginx/Gunicorn）怎么调用你的 Python 代码」的标准协议。开发时用 `runserver` 不需要关心，上线才用到。WSGI 是同步的，ASGI 支持 WebSocket/异步。

### 3.2 创建业务 app

```bash
python manage.py startapp library
```

生成：

```
library/
├── migrations/       ← 数据库变更记录
├── admin.py          ← 后台管理配置
├── apps.py           ← app 元信息
├── models.py         ← 数据模型（★核心）
├── tests.py          ← 测试
├── views.py          ← 视图（★核心）
└── __init__.py
```

`serializers.py`、`tasks.py`、`urls.py`、`management/` 这些 Django **不会自动生成**，要自己建。为什么？因为它们不是必需的——小项目可以不用 DRF、不用 Celery。

本项目额外创建的文件：

```
library/
├── serializers.py            ← 手动创建
├── tasks.py                  ← 手动创建
├── urls.py                   ← 手动创建
└── management/
    ├── __init__.py
    └── commands/
        ├── __init__.py       ← 必须有，否则不是 Python 包
        └── seed_demo.py
```

> **`management/commands/` 目录名不能改。** Django 靠这个固定路径去找自定义命令，改成 `mgmt` 就找不到。

### 3.3 注册 app

打开 [settings.py](file:///home/gyc/Labs/Django-Study/practice/backend/config/settings.py)，在 `INSTALLED_APPS` 里加：

```python
INSTALLED_APPS = [
    # ... Django 自带的 6 个 ...
    "rest_framework",
    "corsheaders",
    "library",          # ← 新加
]
```

**不注册会怎样？** Django 不会加载这个 app 的模型，`makemigrations` 会提示「没有检测到变更」，表永远建不出来。

### 3.4 让 PyMySQL 冒充 mysqlclient

新建 [config/\_\_init\_\_.py](file:///home/gyc/Labs/Django-Study/practice/backend/config/__init__.py)：

```python
import pymysql

pymysql.install_as_MySQLdb()

from .celery import app as celery_app

__all__ = ("celery_app",)
```

为什么要 `install_as_MySQLdb()`？

Django 的 MySQL 后端源码里写死了 `import MySQLdb`。`PyMySQL` 通过这个函数把自己注册到 `sys.modules["MySQLdb"]`，于是 Django 以为装的是 `mysqlclient`，实际用的是纯 Python 驱动。

> 顺序很重要：`install_as_MySQLdb()` 必须在 Django 建立数据库连接**之前**执行。`config/__init__.py` 是最早被导入的文件之一，所以放这里。

`from .celery import app as celery_app` 这行的作用是：Django 启动时顺带加载 Celery 应用，保证 `@shared_task` 能正确绑定到我们的 app 上（第 13 章详解）。

### 3.5 验证骨架

```bash
python manage.py check
```

输出 `System check identified no issues (0 silenced).` 就对了。

如果报 `ModuleNotFoundError: No module named 'MySQLdb'`，说明 `install_as_MySQLdb()` 没生效（多半是文件没保存或放错位置）。

## 第 4 章 读懂 settings.py（逐段讲解）

`settings.py` 是 Django 的「总开关」。不要被 100 多行吓到，实际只有 7 块内容需要理解。

### 4.1 路径与 .env

```python
BASE_DIR = Path(__file__).resolve().parent.parent
load_dotenv(BASE_DIR / ".env")
```

`__file__` 是当前文件（`config/settings.py`）：

```
__file__            → config/settings.py
.parent             → config/
.parent.parent      → backend/      ← BASE_DIR
```

**为什么用 `BASE_DIR / "xxx"` 而不是 `"xxx"`？**
因为相对路径依赖「你从哪个目录启动程序」。用绝对路径，无论你在哪执行 `python manage.py`，都能找到文件。

`.env` 文件内容：

```dotenv
DJANGO_SECRET_KEY=练习项目请换成随机字符串
DJANGO_DEBUG=1

MYSQL_HOST=127.0.0.1
MYSQL_PORT=3307
MYSQL_DB=practice_db
MYSQL_USER=django
MYSQL_PASSWORD=Henhaoji@119

REDIS_CACHE_URL=redis://:Henhaoji%40119@127.0.0.1:6380/2
REDIS_URL=redis://:Henhaoji%40119@127.0.0.1:6380/3
```

**为什么要用 `.env`？**

1. 密码不进 Git（`.gitignore` 里已排除），避免泄露；
2. 本地/测试/生产用不同配置，只换 `.env` 不改代码；
3. 团队协作时，每人 `.env` 不同，代码相同。

> ⚠️ **`Henhaoji%40119` 里的 `%40` 是什么？**
> 这是 URL 编码的 `@`。真实密码是 `Henhaoji@119`。但 Redis 连接串格式是 `redis://:密码@主机:端口/库号`，如果密码里直接写 `@`，解析器会以为 `@` 后面是主机名，导致连不上。所以必须转义：`@` → `%40`。
>
> 这个坑非常常见，记住规则：**URL 里的密码，特殊字符要百分号编码**。

### 4.2 INSTALLED_APPS 与 MIDDLEWARE

```python
MIDDLEWARE = [
    "corsheaders.middleware.CorsMiddleware",   # ← 必须靠前
    "django.middleware.security.SecurityMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "django.contrib.messages.middleware.MessageMiddleware",
    "django.middleware.clickjacking.XFrameOptionsMiddleware",
]
```

**中间件 = 请求的关卡。** 请求从上往下走，响应从下往上返回：

```
请求 → CorsMiddleware → Security → Session → Common → Csrf → ... → 视图
响应 ← CorsMiddleware ← Security ← Session ← Common ← Csrf ← ... ← 视图
```

**为什么 `CorsMiddleware` 要放第一个？**
浏览器的跨域预检请求（`OPTIONS`）需要尽早被处理并返回。如果放在很后面，可能被 `CsrfMiddleware` 先拦掉。


### 4.4 Redis 缓存

```python
CACHES = {
    "default": {
        "BACKEND": "django.core.cache.backends.redis.RedisCache",
```

## 第 5 章 数据建模：为什么要两张表

### 5.1 先想清楚业务

需求：

- 一本书有：书名、作者、价格、库存、所属分类
- 分类有：名称
- 一个分类下有多本书；一本书最多属于一个分类

这就是典型的**一对多（1:N）**关系。

### 5.2 方案对比：为什么不把分类直接存成字符串

**方案 A（新手常见）**：

```python
class Book(models.Model):
    title = models.CharField(max_length=120)
    category = models.CharField(max_length=50)   # 直接存 "技术"
```

问题：

1. **数据冗余**：12 本书里「技术」要存 3 遍，改一次要改 3 处；
2. **容易写错**：`技术` / `技术类` / `tech` 会变成三个不同分类；
3. **没法统计**：想算「技术类有多少本书」只能 `LIKE '%技术%'`；
4. **没法约束**：数据库不知道哪些分类名合法。

**方案 B（本项目）**：分类单独建表，Book 里存分类的 id（外键）。

优点：改名字只改一行、统计只需一个 `COUNT`、数据库层面保证「只能关联真实存在的分类」。

**方案 B 的代价**：查书的时候要多查一次分类表 —— 这就是第 11 章 `select_related` 要解决的问题。

### 5.3 模型代码逐行解释

```python
class Category(models.Model):
    name = models.CharField("分类名称", max_length=50, unique=True)
    created_at = models.DateTimeField("创建时间", auto_now_add=True)

    class Meta:
        ordering = ["id"]
        verbose_name = "分类"
        verbose_name_plural = "分类"

    def __str__(self):
        return self.name
```

| 写法 | 含义 | 为什么 |
| --- | --- | --- |
| `models.CharField` | 短字符串（对应 MySQL `varchar`） | 分类名不会太长 |
| 第一个位置参数 `"分类名称"` | 字段的中文名（verbose name） | admin 后台和报错信息显示中文 |
| `max_length=50` | 最大长度 | MySQL 必填；也防止有人塞 1 万字 |
| `unique=True` | 唯一索引 | 数据库层面禁止「技术」出现两次 |
| `auto_now_add=True` | 创建时自动填当前时间 | 不用手写时间，且不可被客户端篡改 |
| `Meta.ordering` | 默认排序 | 不写的话 MySQL 返回顺序不保证 |
| `__str__` | 打印对象时的显示 | 调试和 admin 下拉框都靠它 |

> **`auto_now_add` 和 `auto_now` 的区别**
> - `auto_now_add=True`：只在**新增**时赋值，之后永远不变（适合 `created_at`）
> - `auto_now=True`：每次**保存**都更新（适合 `updated_at`）
> - 两者都不能在创建时手动传值，测试里要造数据得用 `Book.objects.create()` 之外的技巧。

```python
class Book(models.Model):
    title = models.CharField("书名", max_length=120)
    author = models.CharField("作者", max_length=80, blank=True)
    price = models.DecimalField("价格", max_digits=8, decimal_places=2, default=0)
    stock = models.PositiveIntegerField("库存", default=0)
    category = models.ForeignKey(
        Category,
        verbose_name="分类",
        related_name="books",
        on_delete=models.PROTECT,
        null=True,
        blank=True,
    )
    created_at = models.DateTimeField("创建时间", auto_now_add=True)
```

重点逐个说：

**① `price` 为什么用 `DecimalField` 不用 `FloatField`**

```python
>>> 0.1 + 0.2
0.30000000000000004     # 浮点数用二进制存，无法精确表示 0.1
```

钱的场景不能有这种误差。`DecimalField` 在 MySQL 里对应 `DECIMAL(8,2)`，精确存储。`max_digits=8, decimal_places=2` 表示「总共 8 位数字，其中小数 2 位」，即最大 `999999.99`。

副作用：JSON 里价格是**字符串** `"89.00"`。前端要 `Number(price)` 转一下再算。

**② `stock` 为什么用 `PositiveIntegerField`**

它会在数据库层面加 `CHECK (stock >= 0)` 约束（MySQL 8 支持）。就算有人绕过前端直接发请求，也存不进负数。

**③ `ForeignKey` 的四个参数**

```python
category = models.ForeignKey(
    Category,                    # 关联到哪张表
    verbose_name="分类",         # 中文名
    related_name="books",        # 反向查询名
    on_delete=models.PROTECT,    # 被关联对象删除时怎么办
    null=True, blank=True,       # 允许为空（未分类）
)
```

- **`related_name="books"`**：让你能反向查：
  ```python
  category = Category.objects.get(id=1)
  category.books.all()        # 这个分类下所有书
  category.books.count()      # 有多少本（serializer 里用到）
  ```
  如果不写，默认是 `book_set`，可读性差。

- **`on_delete` 四种常见值（重要）**：

| 值 | 分类被删时 | 适用场景 |
| --- | --- | --- |
| `CASCADE` | 连带删掉所有书 | 订单-订单项（订单没了，明细也没意义） |
| `PROTECT` | **报错，禁止删除** | 本项目：分类还有书就不许删 |
| `SET_NULL` | 书的 category 变成 NULL | 需要 `null=True` |
| `SET_DEFAULT` | 变成默认值 | 有「其他」兜底分类时 |

  本项目选 `PROTECT`，因为「删了分类导致 3 本书凭空消失」是灾难性事故。宁可报错让人先处理书。

- **`null=True` vs `blank=True`（经典混淆点）**：

| 参数 | 管哪一层 | 含义 |
| --- | --- | --- |
| `null=True` | **数据库** | 该列允许存 NULL |
| `blank=True` | **表单校验** | 前端/admin 可以不填 |

字符串字段一般用 `blank=True` + 空字符串（`null=True` 会让「空」有两种表示：NULL 和 ""，很麻烦）。
外键用 `null=True, blank=True`，表示「未分类」。

**④ `Meta.ordering = ["-id"]` 的 `-`**

`-` 表示降序。`["-id"]` = id 从大到小 = 最新添加的在前面。

> ⚠️ 小坑：`Meta.ordering` 会影响所有查询，包括分页。如果你 12 条数据分 3 页，`-id` 排序保证第 1 页永远是最新的。如果没有排序，MySQL 可能返回随机顺序，翻页时会出现「同一条数据在两页都出现」。

## 第 6 章 数据库迁移：makemigrations 到底做了什么

### 6.1 两条命令的分工

```bash
python manage.py makemigrations     # ① 生成「变更说明书」
python manage.py migrate            # ② 照着说明书真正改数据库
```

**为什么不合成一条？**

1. 让你有机会**检查**生成的 SQL（防止误删字段）；
2. 迁移文件可以提交到 Git，团队里别人 `git pull` 后执行 `migrate` 就能同步结构；
3. 生产环境通常「先在测试库跑一遍迁移」再上线。

### 6.2 迁移文件长什么样

执行 `makemigrations` 后，`library/migrations/0001_initial.py` 会生成类似内容：

```python
class Migration(migrations.Migration):
    initial = True
    dependencies = []
    operations = [
        migrations.CreateModel(
            name="Category",
            fields=[
                ("id", models.BigAutoField(auto_created=True, primary_key=True, ...)),
                ("name", models.CharField(max_length=50, unique=True, verbose_name="分类名称")),
                ("created_at", models.DateTimeField(auto_now_add=True, verbose_name="创建时间")),
            ],
            options={"ordering": ["id"], "verbose_name": "分类", "verbose_name_plural": "分类"},
        ),
        migrations.CreateModel(
            name="Book",
            fields=[
                ("id", models.BigAutoField(...)),
                ("title", models.CharField(max_length=120, verbose_name="书名")),
                ...
                ("category", models.ForeignKey(
                    blank=True, null=True, on_delete=django.db.models.deletion.PROTECT,
                    related_name="books", to="library.category", verbose_name="分类",
                )),
            ],
            options={"ordering": ["-id"], ...},
        ),
    ]
```

**关键理解：迁移文件是「代码」不是「结果」。** 它描述的是「怎么从旧结构变到新结构」，Django 按顺序执行这些操作。

### 6.3 看看真正的 SQL

```bash
python manage.py sqlmigrate library 0001
```

输出类似：

```sql
CREATE TABLE `library_category` (
    `id` bigint AUTO_INCREMENT NOT NULL PRIMARY KEY,
    `name` varchar(50) NOT NULL UNIQUE,
    `created_at` datetime(6) NOT NULL
);

CREATE TABLE `library_book` (
    `id` bigint AUTO_INCREMENT NOT NULL PRIMARY KEY,
    `title` varchar(120) NOT NULL,
    `author` varchar(80) NOT NULL,
    `price` decimal(8, 2) NOT NULL,
    `stock` integer UNSIGNED NOT NULL CHECK (`stock` >= 0),
    `created_at` datetime(6) NOT NULL,
    `category_id` bigint NULL,
    FOREIGN KEY (`category_id`) REFERENCES `library_category` (`id`)
);
```

几个细节印证前面的说法：

- `decimal(8, 2)` ← `max_digits=8, decimal_places=2`
- `CHECK (stock >= 0)` ← `PositiveIntegerField`
- `FOREIGN KEY ... REFERENCES` ← `ForeignKey`
- **表名规则**：`<app名>_<模型名小写>` → `library_book`
- **外键列名规则**：`<字段名>_id` → `category_id`

> **为什么表名有个 `library_` 前缀？** 因为 Django 允许多个 app 有同名模型（比如两个 app 都有 `Category`），加前缀避免冲突。想改可以用 `Meta.db_table`。

### 6.4 执行迁移

```bash
python manage.py migrate
```

你会看到它不只建了我们两张表，还建了 `auth_user`、`django_session`、`django_migrations` 等一堆。那是因为 `INSTALLED_APPS` 里的 `django.contrib.*` 也需要表。

其中 **`django_migrations` 表记录「哪些迁移已经执行过」**。所以 `migrate` 重复执行是安全的，不会重复建表。

### 6.5 改模型之后的标准动作

```
改 models.py
   ↓
python manage.py makemigrations     ← 生成 0002_xxx.py
   ↓
python manage.py migrate            ← 应用到数据库
```

**常见错误**：

| 报错 | 原因 | 解决 |
| --- | --- | --- |
| `No changes detected` | app 没加到 `INSTALLED_APPS`，或文件没保存 | 检查 settings 和保存状态 |
| `Table already exists` | 手动建过同名表 | 删表或 `--fake`（慎用） |
| `You are trying to add a non-nullable field` | 新增必填字段但表里已有数据 | 加 `null=True` 或给 `default` |

### 6.6 回滚迁移

```bash
python manage.py migrate library 0001     # 回到 0001 状态
python manage.py migrate library zero     # 全部撤销（删表）
```

> 生产环境慎用回滚。删字段的迁移一旦执行，数据就没了。正确做法是「新增字段代替删除字段」（先加新字段 → 迁数据 → 删旧字段）。

## 第 7 章 Admin 后台：不写前端也能管理数据

### 7.1 为什么先做 Admin

新手常见误区：一上来就写前端。结果接口还没调通，前端一堆报错，根本分不清是前端问题还是后端问题。

Admin 是 Django 送的「现成管理界面」，**零前端代码**就能增删改查。用它先确认「数据库和模型是通的」，再写接口，最后写前端。排查问题范围能缩小 2/3。

### 7.2 三个步骤

**① 建超级用户**

```bash
python manage.py createsuperuser
# Username: admin
# Email: （直接回车跳过）
# Password: 输入两次（太简单的密码会被拒绝）
```

**② 注册模型**（[library/admin.py](file:///home/gyc/Labs/Django-Study/practice/backend/library/admin.py)）

```python
@admin.register(Category)
class CategoryAdmin(admin.ModelAdmin):
    list_display = ["id", "name", "created_at"]
    search_fields = ["name"]


@admin.register(Book)
class BookAdmin(admin.ModelAdmin):
    list_display = ["id", "title", "author", "price", "stock", "category", "created_at"]
    list_filter = ["category"]
    search_fields = ["title", "author"]
    list_editable = ["stock"]
```

| 配置 | 效果 |
| --- | --- |
| `list_display` | 列表页显示哪些列 |
| `search_fields` | 右上角搜索框搜哪些字段 |
| `list_filter` | 右侧筛选面板 |
| `list_editable` | 列表页直接编辑（不用点进去） |

> ⚠️ `list_editable` 里的字段**必须同时出现在 `list_display` 里**，否则 Django 启动直接报错（`'list_editable' refers to field 'stock' which is not in 'list_display'`）。

### 7.4 试试 PROTECT 的效果

## 第 8 章 Serializer：模型和 JSON 之间的翻译官

### 8.1 为什么需要 Serializer

数据库里存的是 Python 对象：

```python
<Book: Python 编程从入门到实践>   # 内存里的对象，不是 JSON
```

浏览器只认 JSON 字符串。中间需要一个「翻译」：

```
模型对象 ──序列化──▶ Python dict ──▶ JSON 字符串 ──▶ 浏览器
模型对象 ◀─反序列化── Python dict ◀── JSON 字符串 ◀── 浏览器
```

DRF 的 `Serializer` 就是干这个的。而且它还负责**校验**（价格不能为负、书名不能为空等）。

### 8.2 ModelSerializer 帮你做了什么

```python
class BookSerializer(serializers.ModelSerializer):
    class Meta:
        model = Book
        fields = ["id", "title", "author", "price", "stock", "category", "category_name", "created_at"]
```

只要写 `model` + `fields`，DRF 会自动：

1. 按模型字段类型生成对应序列化字段（`DecimalField` → 字符串，`PositiveIntegerField` → 整数）；
2. 生成基础校验（`max_length`、`unique`、外键存在性）；
3. 生成 `create()` / `update()` 方法（直接调 ORM）。

**对比手写**：如果用普通 `Serializer`，每个字段都要自己声明，`create`/`update` 也要自己写，20 行变 100 行。

### 8.3 三个「进阶字段」逐个讲

**① `source="books.count"`**

```python
class CategorySerializer(serializers.ModelSerializer):
    book_count = serializers.IntegerField(source="books.count", read_only=True)
```

意思是：这个字段的值 = `obj.books.count()`。

- `books` 是 `related_name` 定义的反向管理器；
- DRF 会沿着 `source` 的点号路径取值并**调用**末尾的可调用对象。

效果：

```json
{"id": 1, "name": "技术", "book_count": 3}
```

`read_only=True` 表示只读（客户端传了也忽略），因为数量是算出来的，不能直接写。

> ⚠️ **性能警告**：分类有 N 个，就会执行 N+1 次 `COUNT` 查询。本项目分类只有 4 个无所谓。分类上千时要用 `annotate(Count("books"))` 优化（见 21 章练习 2）。

**② `SerializerMethodField`**

```python
class BookSerializer(serializers.ModelSerializer):
    category_name = serializers.SerializerMethodField()

    def get_category_name(self, obj):
        return obj.category.name if obj.category else "未分类"
```

用途：返回模型里**不存在**的字段。

这里的需求是：写数据时前端只需要传 `category: 1`（id），但读数据时需要显示 `"技术"`（名字）。所以：

- `category` 字段 → 可写，返回 id
- `category_name` 字段 → 只读，返回名字

方法名规则：`get_<字段名>`，参数 `obj` 是当前实例。

**③ `read_only_fields`**

```python
read_only_fields = ["id", "created_at"]
```

防止客户端篡改：

```bash
# 恶意请求
curl -X POST /api/books/ -d '{"id": 1, "created_at": "2000-01-01T00:00:00Z", ...}'
```

如果没设 `read_only`，`id` 和 `created_at` 会被前端传的值覆盖（导致主键冲突或时间造假）。

### 8.4 自定义校验 `validate_<字段名>`

```python
def validate_price(self, value):
    if value < 0:
        raise serializers.ValidationError("价格不能为负数")
    return value
```

**命名规则决定一切**：方法名叫 `validate_price`，DRF 就自动拿它校验 `price` 字段。

DRF 的完整校验流程：

```
客户端 JSON
   ↓ to_internal_value（类型转换："89.00" → Decimal("89.00")）
   ↓ 每个字段的默认校验（max_length、required...）
   ↓ validate_<字段名>（你的自定义校验）  ← 这里
   ↓ validate（整个对象的联合校验，比如"开始时间不能晚于结束时间"）
   ↓ create() / update() → 存数据库
```

抛 `ValidationError` 会自动变成 HTTP 400 + JSON：

```json
{"price": ["价格不能为负数"]}
```

**为什么模型层已经有 `PositiveIntegerField` 校验了，还要在这里再写一遍？**

因为数据库约束报的错是英文的、且是 500 级别的（在 MySQL 严格模式下会抛 `IntegrityError`）。放在 serializer 里能返回结构化的中文 400 错误，前端好处理。

**分层原则**：
- 数据库约束 → 最后一道防线（防绕过）
- Serializer 校验 → 用户体验层（给人看）
- 前端校验 → 最快反馈（但不安全，可绕过）

## 第 9 章 ViewSet + Router：6 个接口是怎么自动生成的

### 9.1 从「手写视图」到「ViewSet」

**最低级写法（APIView）**，每个接口一个类：

```python
class BookListView(APIView):
    def get(self, request):
        books = Book.objects.all()
        return Response(BookSerializer(books, many=True).data)

class BookDetailView(APIView):
    def get(self, request, pk):
        book = Book.objects.get(pk=pk)
        return Response(BookSerializer(book).data)
# ... 还有 POST / PUT / PATCH / DELETE 要写
```

6 个接口 = 6 个类 + 6 条路由，重复代码多。

**ViewSet 写法**：把「一组相关操作」放进一个类：

```python
class BookViewSet(viewsets.ModelViewSet):
    queryset = Book.objects.all()
    serializer_class = BookSerializer
```

就这么几行，DRF 已经实现好了：

| 方法 | URL | 动作 | 内部调用 |
| --- | --- | --- | --- |
| GET | `/api/books/` | 列表 | `list()` |
| POST | `/api/books/` | 新增 | `create()` |
| GET | `/api/books/{id}/` | 详情 | `retrieve()` |
| PUT | `/api/books/{id}/` | 全量改 | `update()` |
| PATCH | `/api/books/{id}/` | 局部改 | `partial_update()` |
| DELETE | `/api/books/{id}/` | 删除 | `destroy()` |

### 9.2 Router：URL 也是自动生成的

```python
router = DefaultRouter()
router.register("categories", CategoryViewSet, basename="category")
router.register("books", BookViewSet, basename="book")

urlpatterns = [
    path("", include(router.urls)),
]
```

`register` 一行 = 2 条路由（列表 + 详情），并且自动带上 API 根视图。

**`basename` 是什么？** 路由的命名前缀，用于反向解析（`reverse("book-list")`）。如果 ViewSet 里有 `queryset`，Django 能自动推断，可以不写；但显式写更清晰。

### 9.3 Mixin 与 MRO：为什么 `CachedListMixin` 要写在前面

```python
class BookViewSet(CachedListMixin, viewsets.ModelViewSet):
```

**MRO（Method Resolution Order，方法查找顺序）**：Python 从左到右找方法。

```
BookViewSet
   ├── ① CachedListMixin      ← 先找这里
   └── ② ModelViewSet         ← 再找这里
```

所以 `list()` 会先用 `CachedListMixin.list`，它里面再 `super().list()` 调回 DRF 的默认实现。

**如果顺序反了会怎样？**

```python
class BookViewSet(viewsets.ModelViewSet, CachedListMixin):   # 错误
```

`ModelViewSet.list` 先被找到，直接返回结果，**永远不会执行缓存逻辑**。这是 Python 多继承最常见的坑，没有报错，只是静默失效。

> **怎么验证？** 在 `CachedListMixin.list` 里加一行 `print("cache path")`，请求两次看是否打印两次。或者看响应里有没有 `X-Cache` 头（可以自己加）。

### 9.4 `get_queryset()`：动态决定查哪些数据

```python
def get_queryset(self):
    queryset = Book.objects.select_related("category").all()

    category_id = self.request.query_params.get("category")
    if category_id:
        try:
            queryset = queryset.filter(category_id=int(category_id))
        except (TypeError, ValueError):
            queryset = queryset.none()

    return queryset
```

**为什么要重写 `get_queryset` 而不是直接用 `queryset = Book.objects.all()`？**

因为要支持 `?category=3` 这种动态筛选。`queryset` 是类属性（所有请求共享），不能在里面读 `self.request`。`get_queryset()` 每次请求都会重新执行，才能拿到当前请求的参数。

**`queryset.none()` 是什么？** 返回一个永远为空的结果集。相比直接 `raise ValidationError`，它的好处是：前端拿到的是「空列表 + count=0」，页面正常显示「暂无数据」，而不是一个红色错误弹窗。

> 设计取舍：`?category=abc` 到底该报错还是返回空？
> - 报错（400）：更严格，能帮前端发现 bug
> - 返回空：更宽容，页面不会崩
>
> 本项目选后者（学习项目，容错优先）。真实 API 建议返回 400。

### 9.5 删除保护：把 `ProtectedError` 翻译成中文

```python
def perform_destroy(self, instance):
    try:
        instance.delete()
    except ProtectedError:
        raise ValidationError({"detail": "该分类下还有图书，不能删除"})
    bump_cache_version()
```

`perform_destroy` 是 `destroy()` 内部调用的钩子，默认只做一件事：`instance.delete()`。重写它就能在删除前后加逻辑。

- `ProtectedError` 是 `django.db.models` 里的异常，由 `PROTECT` 触发；
- `rest_framework.exceptions.ValidationError` 会被 DRF 捕获并转成 **400**；
- 若不捕获，`ProtectedError` 会变成 **500**（服务器错误），前端只能看到「服务器开小差了」。

**为什么要包一层？** 500 意味着「这是服务端的 bug」，会让监控报警；400 意味着「你的请求有问题」，是预期内的业务规则。语义完全不一样。

### 9.6 两个 APIView：健康检查与任务接口

不是所有接口都适合 ViewSet。比如 `/api/health/`，它不是对某个「资源」的增删改查，用最朴素的 `APIView` 更直接：

```python
class HealthView(APIView):
    def get(self, request):
        try:
            connection.ensure_connection()
            db_ok = True
        except Exception:
            db_ok = False

        try:
            cache.set("library:health", "ok", timeout=10)
            redis_ok = cache.get("library:health") == "ok"
        except Exception:
            redis_ok = False

        status_text = "ok" if db_ok and redis_ok else "degraded"
        return Response(
            {"status": status_text, "db": db_ok, "redis": redis_ok},
            status=200 if status_text == "ok" else 503,
        )
```

**为什么健康检查要真的读一次 Redis 而不是只判断「配置存在」？**
配置存在不代表连得上（密码错、容器挂了、网络不通）。真实探测才能发现问题。

**为什么失败返回 503 而不是 500？**
503 = Service Unavailable（服务暂时不可用），是给负载均衡/监控看的标准信号。

### 9.7 路由顺序的坑

```python
urlpatterns = [
    path("health/", HealthView.as_view()),
    path("tasks/report/", StockReportTaskView.as_view()),
    path("tasks/<str:task_id>/", TaskStatusView.as_view()),
    path("", include(router.urls)),
]
```

**为什么 `tasks/report/` 必须写在 `tasks/<str:task_id>/` 前面？**

Django 的 URL 匹配是**从上到下、找到第一个匹配就停**：

- 如果 `<str:task_id>` 在前，访问 `tasks/report/` 时 `report` 会被当成 `task_id`；
- `TaskStatusView` 收到 `task_id="report"`，去查 Celery 任务，返回 `PENDING`，永远查不到。

**通用规则：具体的静态路径一定写在变量路径前面。**

### 9.8 完整请求旅程

以「前端点搜索」为例，走一遍全链路：

```
① 浏览器 GET http://localhost:5174/api/books/?search=python&page=1
② Vite 代理转发 → http://127.0.0.1:8001/api/books/?search=python&page=1
③ Django 总路由 config/urls.py 匹配 "api/" → 进入 library.urls
④ library.urls 匹配 "" → router 的 books 列表路由
⑤ 请求方法 GET → 调用 BookViewSet.list()
⑥ list() 是 CachedListMixin 的版本 → 先算缓存 key
⑦ 未命中 → super().list()
⑧ ModelViewSet.list → 过滤器后端（SearchFilter 加 WHERE title LIKE ...）
⑨ 分页器（LIMIT 5）
⑩ BookSerializer 序列化 → JSON
⑪ 写入缓存
⑫ 原路返回 → 浏览器
```

能把这 12 步说清楚，你就算真的理解这套架构了。

## 第 10 章 分页、搜索、排序

### 10.1 分页：为什么后端分页，不是前端分页

**前端分页**：一次拿 10000 条，JS 里 `slice`。
- 优点：翻页快（数据已在本地）
- 缺点：首屏慢、流量大、内存爆

**后端分页**：一次拿 5 条。
- 优点：首屏快、省流量
- 缺点：每次翻页都要请求

数据量超过 100 条就该后端分页。

### 10.2 `PageNumberPagination` 的响应结构

配置：

```python
"DEFAULT_PAGINATION_CLASS": "rest_framework.pagination.PageNumberPagination",
"PAGE_SIZE": 5,
```

响应：

```json
{
  "count": 12,
  "next": "http://127.0.0.1:8001/api/books/?page=2",
  "previous": null,
  "results": [ {...}, {...}, {...}, {...}, {...} ]
}
```

| 字段 | 含义 | 前端怎么用 |
| --- | --- | --- |
| `count` | 总条数 | 算总页数 `Math.ceil(count / 5)` |
| `next` | 下一页 URL | 一般不用（前端自己维护页码） |
| `previous` | 上一页 URL | 同上 |
| `results` | 当前页数据 | 渲染表格 |

**为什么不用 `next`/`previous`？** 因为它们带完整域名，前端如果直接用会绕过代理、变成跨域请求。前端用 `?page=N` 自己拼更可控。

### 10.3 关闭分页：为什么分类接口不需要

```python
class CategoryViewSet(...):
    pagination_class = None
```

两个原因：

1. 分类只有几个，分页没意义；
2. 前端下拉框需要**一次性拿到全部**分类。如果分类接口也分页，下拉框只能显示前 5 个，用户体验灾难。

**关闭分页后响应结构变了**：

```json
// 开启分页
{"count": 12, "results": [...]}

// 关闭分页（直接是数组！）
[{"id": 1, "name": "技术"}, ...]
```

**前端必须配合改**：

```js
// 图书（有分页）
this.books = data.results
this.total = data.count

// 分类（无分页）
this.categories = data      // 直接就是数组
```

如果这里搞错，会出现 `data.results is undefined` 或表格渲染出 `count` 字样。

### 10.4 搜索

```python
search_fields = ["title", "author"]
```

配合全局的 `SearchFilter`，请求 `?search=python` 会生成：

```sql
WHERE (title LIKE '%python%' OR author LIKE '%python%')
```

**特点**：
- 大小写不敏感（MySQL `utf8mb4_unicode_ci` 排序规则）；
- 是 `%关键词%` 的前后模糊匹配，**索引会失效**，数据量大时很慢；
- 多个词用空格分隔 = AND 关系（`?search=python django`）。

**什么时候会变慢？** 10 万条以上。解决方案：全文索引（MySQL `FULLTEXT`）、Elasticsearch、或至少改成「前缀匹配」`python%`。

### 10.5 排序

```python
ordering_fields = ["id", "title", "price", "stock", "created_at"]
ordering = ["-id"]     # 默认
```

请求 `?ordering=-price` → 价格降序；`?ordering=title` → 书名升序。

**为什么要限制 `ordering_fields`？**

如果不限制，用户能传任意字段（包括外键关联字段），可能：
1. 触发意外的全表扫描；
2. 报错 `FieldError: Cannot resolve keyword`（500）。

限制白名单是安全实践。

### 10.6 前端分页逻辑

```js
computed: {
  totalPages() {
    return Math.max(1, Math.ceil(this.total / this.pageSize))
  }
}
```

- `Math.ceil`：总数 12 / 每页 5 = 2.4 → 3 页；
- `Math.max(1, ...)`：没数据时也显示「第 1 / 1 页」，而不是「第 1 / 0 页」。

**删掉最后一页唯一一条数据时会发生什么？**

```
第 3 页只有 1 条 → 删掉 → 请求 page=3 → 后端返回 count=10, results=[]
```

页面会显示空表格。所以代码里加了越界修正：

```js
if (this.page > this.totalPages) {
  this.page = this.totalPages
  this.loadBooks()
}
```

## 第 11 章 查数据库的性能坑：N+1 与 select_related

### 11.1 什么是 N+1 查询

假设要序列化 5 本书，每本都要显示分类名：

```python
# 序列化器里
def get_category_name(self, obj):
    return obj.category.name
```

**不加优化时，Django 实际执行的 SQL**：

```sql
-- 第 1 次：查书
SELECT * FROM library_book LIMIT 5;

-- 然后每本书都要查一次分类（因为 obj.category 还没加载）
SELECT * FROM library_category WHERE id = 1;   -- 书1
SELECT * FROM library_category WHERE id = 1;   -- 书2
SELECT * FROM library_category WHERE id = 2;   -- 书3
SELECT * FROM library_category WHERE id = 2;   -- 书4
SELECT * FROM library_category WHERE id = 1;   -- 书5
```

**1 次主查询 + N 次关联查询 = N+1 问题。**

5 条数据看不出问题，500 条就是 501 次查询，接口慢 100 倍。

### 11.2 `select_related` 怎么解决

```python
Book.objects.select_related("category").all()
```

生成的 SQL：

```sql
SELECT book.*, category.*
FROM library_book
LEFT OUTER JOIN library_category ON book.category_id = category.id
LIMIT 5;
```

**一次 JOIN 搞定**，1 次查询而不是 6 次。

原理：`select_related` 让 Django 在 SQL 层做 JOIN，把关联表的数据一起取回来，缓存到 `obj.category` 上。之后访问 `obj.category.name` 不再发 SQL。

### 11.3 `select_related` vs `prefetch_related`

| | `select_related` | `prefetch_related` |
| --- | --- | --- |
| 关联类型 | `ForeignKey`、`OneToOneField`（多对一/一对一） | `ManyToManyField`、反向外键（一对多） |
| 实现 | SQL `JOIN` | 两条 SQL + Python 里拼装 |
| SQL 次数 | 1 次 | 2 次 |

**判断口诀**：从「多」查「一」用 `select_related`，从「一」查「多」用 `prefetch_related`。

本项目：

```python
Book.objects.select_related("category")            # Book → Category（多对一）✓
Category.objects.prefetch_related("books")         # Category → Book（一对多）✓
```

### 11.4 怎么发现 N+1

**方法 1：Django Debug Toolbar**（可视化，最直观）

```bash
pip install django-debug-toolbar
```

**方法 2：打印 SQL**

```python
from django.db import connection
print(len(connection.queries))   # 查询次数
```

**方法 3：`assertNumQueries`（写测试时）**

```python
def test_list_queries(self):
    with self.assertNumQueries(1):
        list(Book.objects.select_related("category")[:5])
```

### 11.5 本项目的取舍说明

`BookViewSet.get_queryset()` 用了 `select_related`，因为**每页都要显示分类名**，收益明显。

`CategorySerializer` 的 `book_count = source="books.count"` **没有优化**，因为：

- 分类总数只有 4 个，N+1 = 5 次查询，可忽略；
- 优化写法会复杂不少（`annotate`），学习阶段先求「看懂」。

**优化版本**（第 21 章练习 2 会让你自己写）：

```python
from django.db.models import Count

class CategoryViewSet(...):
    def get_queryset(self):
        return Category.objects.annotate(book_count=Count("books"))

class CategorySerializer(...):
    book_count = serializers.IntegerField(read_only=True)   # 直接用 annotate 出来的字段
```

**要不要为了 4 个分类优化？不要。** 过早优化是万恶之源。等你真的遇到 1000 个分类再改，改起来也就 10 分钟。

✅ **本章验收**

在 `get_queryset` 里临时加 `print(queryset.query)`，观察生成的 SQL 里有没有 `JOIN`。

## 第 12 章 Redis 缓存：为什么用「版本号」而不是删 key

### 12.1 为什么要缓存

图书列表接口每次要做：解析参数 → 查 MySQL → 序列化 → JSON 编码。

数据没变时，这一整套是**重复劳动**。把结果缓存 30 秒，99% 的请求直接返回，MySQL 压力骤降。

**适合缓存的数据**：读多写少、允许短暂不一致。
**不适合**：余额、库存扣减、订单状态（必须强一致）。

> 注意：本项目的缓存只用在**列表展示**上。真实下单扣库存绝对不能走缓存的旧值，必须在数据库里用 `SELECT ... FOR UPDATE` 或原子更新。

### 12.2 Django 缓存 API 三件套

```python
from django.core.cache import cache

cache.set("key", value, timeout=30)    # 存 30 秒
cache.get("key")                       # 取，没有返回 None
cache.delete("key")                    # 删
```

底层可以是内存、文件、Redis。配置里指定了 `RedisCache`，所以存在 Redis 2 号库。

### 12.3 核心难题：数据变了，缓存怎么失效

假设缓存了 `/api/books/?page=1` 的结果。现在新增一本书，缓存里还是旧的 12 条。必须让缓存失效。

**方案 A：`cache.delete()` 逐个删**

问题：一个列表可能有无数种参数组合：

```
/api/books/?page=1
/api/books/?page=2
/api/books/?page=3
/api/books/?search=python
/api/books/?category=1&page=1
/api/books/?ordering=-price&page=2
...
```

组合爆炸，根本删不完。

**方案 B：`delete_pattern("library:books:*")`**

Django 的 Redis 后端**原生不支持** `delete_pattern`（这是 `django-redis` 三方库的功能）。即使支持，`KEYS *` 在大数据量下会阻塞 Redis（`KEYS` 是 O(N) 且单线程阻塞）。

**方案 C：版本号（本项目采用）**

```
缓存 key = library:books:<版本号>:<完整URL>

初始：library:books:1700000000:/api/books/?page=1
新增书 → 版本号换成 1700000050
读取：library:books:1700000050:/api/books/?page=1  ← 新 key，老 key 已失效
```

**旧 key 不用删**，30 秒后自动过期消失。写操作只改一个 Redis key。

### 12.4 代码实现拆解

```python
CACHE_VERSION_KEY = "library:cache_version"
LIST_CACHE_TIMEOUT = 30

def get_cache_version():
    version = cache.get(CACHE_VERSION_KEY)
    if version is None:
        version = time.time_ns()          # 纳秒级时间戳，永不为 0
        cache.set(CACHE_VERSION_KEY, version, timeout=None)   # timeout=None 永不过期
    return version

def bump_cache_version():
    cache.set(CACHE_VERSION_KEY, time.time_ns(), timeout=None)

def build_cache_key(prefix, request):
    return f"library:{prefix}:{get_cache_version()}:{request.get_full_path()}"
```

**为什么版本号用时间戳而不是自增 1？**

| 方案 | 并发问题 |
| --- | --- |
| `version += 1` | 两个请求同时读 1、同时写 2，只涨了 1；且需要「读-改-写」，不是原子操作 |
| `time.time_ns()` | 纳秒级，两次调用必然不同；单条 `SET` 命令天然原子 |

**为什么用 `get_full_path()` 而不是自己拼参数？**

`?page=2&search=x` 和 `?search=x&page=2` 参数顺序不同但语义相同，会生成两个 key。这是「缓存命中率低」的小问题，但换来代码简单。真实项目可以改成对参数排序后拼接。

### 12.5 Mixin 的实现与 MRO

```python
class CachedListMixin:
    cache_prefix = "list"

    def list(self, request, *args, **kwargs):
        key = build_cache_key(self.cache_prefix, request)
        cached = cache.get(key)
        if cached is not None:
            return Response(cached)          # 命中，直接返回

        response = super().list(request, *args, **kwargs)   # 未命中，查库
        cache.set(key, response.data, timeout=LIST_CACHE_TIMEOUT)
        return response

    def perform_create(self, serializer):
        serializer.save()
        bump_cache_version()

    def perform_update(self, serializer):
        serializer.save()
        bump_cache_version()

    def perform_destroy(self, instance):
        instance.delete()
        bump_cache_version()
```

**为什么 `response.data` 不能套 `dict()`？**

`response.data` 有两种形态：

```python
# 开启分页 → ReturnDict（字典）
{"count": 12, "next": None, "previous": None, "results": [...]}

# 关闭分页 → ReturnList（列表）
[{"id": 1, "name": "技术"}, ...]
```

对列表套 `dict()` 会报：

```
ValueError: dictionary update sequence element #0 has length 4; 2 is required
```

（因为它试图把 `{"id": 1, ...}` 当成 `(key, value)` 二元组，但长度是 4。）

这个 bug 在本项目里真实发生过 —— `CategoryViewSet` 关了分页，一请求就 500。所以现在直接存 `response.data`，DRF 的 ReturnDict/ReturnList 本身能被 Redis 正确序列化。

### 12.6 `perform_*` 钩子为什么好用

DRF 的 `create()` 内部流程：

```
create()
  ├── 校验 serializer
  ├── perform_create(serializer)   ← 钩子
  └── 返回 201 + 数据
```

以及 `destroy()`：

```
destroy()
  ├── get_object()
  ├── perform_destroy(instance)    ← 钩子
  └── 返回 204
```

重写钩子比重写整个 `create()` 更安全：默认逻辑（校验、状态码、响应头）都保留，只插自己的逻辑。

## 第 13 章 Celery：把慢操作丢到后台

### 13.1 先看问题

假设生成库存报表要 5 秒。如果直接在接口里算：

```
用户点按钮 → 请求 /api/tasks/report/ → 后端算 5 秒 → 返回结果
                                    ↑
                              这 5 秒浏览器一直转圈
```

如果同时 100 个用户点，Django 的进程/线程会被占满，**整个网站都卡住**（包括本来就很快的图书列表）。

### 13.2 三个角色

Celery 把「接请求的人」和「干活的人」分开：

```
① 生产者（Django）      ② 队列（Redis）        ③ 消费者（Celery worker）
   "帮我算个报表"   →   [任务1, 任务2, ...]   →   一个一个取出来算
   立刻返回 task_id                              算完把结果写回 Redis
                                                      ↓
                                              ④ 结果存储（Redis）
```

| 名词 | 是什么 | 本项目对应 |
| --- | --- | --- |
| Broker（中间人） | 存「待执行任务」的队列 | Redis 3 号库 |
| Worker（工人） | 单独的进程，从队列取任务执行 | `celery -A config worker` |
| Backend（结果存储） | 存任务执行结果 | Redis 3 号库 |
| task_id | 任务的唯一编号（UUID） | 返回给前端，用来查结果 |

**为什么 Broker 和 Backend 可以共用一个 Redis 库？** 因为它们用不同的 key 前缀（`celery` 和 `celery-task-meta-`），不会冲突。生产环境量大时会拆开。

### 13.3 三段代码

**① 创建 Celery 应用**（[config/celery.py](file:///home/gyc/Labs/Django-Study/practice/backend/config/celery.py)）

```python
import os
from celery import Celery

os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings")

app = Celery("library_practice")
app.config_from_object("django.conf:settings", namespace="CELERY")
app.autodiscover_tasks()
```

| 行 | 作用 | 不写会怎样 |
| --- | --- | --- |
| `setdefault("DJANGO_SETTINGS_MODULE", ...)` | 告诉 Celery 用哪份 Django 配置 | worker 启动时报 `ImproperlyConfigured` |
| `Celery("library_practice")` | 应用名，也是队列名前缀 | 多个项目共用 Redis 时任务互相串（见下） |
| `config_from_object(..., namespace="CELERY")` | 从 settings 读 `CELERY_*` 配置 | 连不上 Redis，去连默认的 RabbitMQ |
| `autodiscover_tasks()` | 自动扫描每个 app 的 `tasks.py` | 任务注册不上，`.delay()` 报 `NotRegistered` |

> **为什么要给 app 起个名字？** 默认队列名是 `celery`。如果主项目和练习项目共用 Redis 且都用默认名，两边的 worker 会抢对方的任务，然后报「不认识这个任务」。起不同名字（或用不同 Redis 库）就能隔离。本项目用了不同的库（3 号），双保险。

**② 定义任务**（[library/tasks.py](file:///home/gyc/Labs/Django-Study/practice/backend/library/tasks.py)）

```python
@shared_task
def generate_stock_report(delay_seconds=2):
    time.sleep(delay_seconds)

    total_titles = Book.objects.count()
    total_stock = Book.objects.aggregate(total=Sum("stock"))["total"] or 0
    total_value = (
        Book.objects.aggregate(total=Sum(F("stock") * F("price")))["total"]
        or Decimal("0")
    )

    return {
        "total_titles": total_titles,
        "total_stock": total_stock,
        "total_value": str(total_value),
    }
```

**为什么用 `@shared_task` 而不是 `@app.task`？**

`@shared_task` 不绑定具体 app 实例，写在 app 内部不会产生循环导入（`tasks.py` 导入 `celery.py`，`celery.py` 又要发现 `tasks.py`，容易成环）。**Django 项目一律用 `@shared_task`。**

**为什么故意 `sleep(2)`？**

本地数据只有 12 条，真实计算 1 毫秒就完。不加延迟，你根本看不到 `PENDING → STARTED → SUCCESS` 的过程，也体会不到异步的价值。

**`F("stock") * F("price")` 是什么？**

`F()` 表示「引用数据库里的字段」，让 MySQL 在数据库端算乘法：

```sql
SELECT SUM(stock * price) FROM library_book;
```

如果写成 Python 循环：

```python
total = sum(b.stock * b.price for b in Book.objects.all())   # ❌
```

会把 1 万本书全部读进内存再算，慢且吃内存。**能交给数据库算的就交给数据库。**

**为什么 `total_value` 要 `str()`？**

`Decimal` 不是 JSON 原生类型，Celery 序列化（默认 JSON）会报 `TypeError: Object of type Decimal is not JSON serializable`。转字符串最省事，前端展示也不需要再算。

**`or Decimal("0")` 为什么需要？**

`aggregate()` 在没有数据时返回 `{"total": None}`。`Sum` 的空集结果就是 NULL，不是 0。不兜底的话，`str(None)` 会得到 `"None"`，前端显示 `total_value: "None"`。

**③ 提交与查询**（[library/views.py](file:///home/gyc/Labs/Django-Study/practice/backend/library/views.py#L191-L217)）

```python
class StockReportTaskView(APIView):
    def post(self, request):
        task = generate_stock_report.delay()
        return Response({"task_id": task.id}, status=status.HTTP_202_ACCEPTED)


class TaskStatusView(APIView):
    def get(self, request, task_id):
        result = AsyncResult(task_id)
        payload = {"task_id": task_id, "status": result.status}
        if result.successful():
            payload["result"] = result.result
        elif result.failed():
            payload["error"] = str(result.result)
        return Response(payload)
```

**`.delay()` vs 直接调用**：

```python
generate_stock_report()          # 同步：当前进程卡 2 秒
generate_stock_report.delay()    # 异步：只往 Redis 塞一条消息，1 毫秒返回
```

**为什么返回 202 而不是 200？**

202 = Accepted（已接受，正在处理）。语义上「我没算完，但我知道你提交了」。200 会让调用方以为结果就在响应里。

### 13.4 任务状态机

| 状态 | 含义 | 什么时候出现 |
| --- | --- | --- |
| `PENDING` | 还没开始 / 或 task_id 不存在 | 刚提交，worker 还没取到 |
| `STARTED` | 正在执行 | 需要 `CELERY_TASK_TRACK_STARTED = True` |
| `SUCCESS` | 成功，有结果 | 正常结束 |
| `FAILURE` | 抛异常了 | 代码报错 |
| `RETRY` | 正在重试 | 配合 `autoretry_for` |

> ⚠️ **重要陷阱**：`PENDING` 是「默认值」，它同时代表「排队中」和「这个 task_id 根本不存在」。所以如果你写错 task_id，永远看到 `PENDING`，不会报 404。

### 13.6 前端为什么用「轮询」而不是 WebSocket

```js
async pollReport(taskId) {
  for (let i = 0; i < 12; i += 1) {
    await new Promise((resolve) => setTimeout(resolve, 700))
    const { data } = await http.get(`/tasks/${taskId}/`)
    this.reportTask = data
    if (data.status === 'SUCCESS' || data.status === 'FAILURE') return
  }
}
```

**轮询**（本项目）：每 700ms 问一次「好了吗」，最多问 12 次（约 8.4 秒）。
- 优点：实现极简，不需要额外基础设施
- 缺点：有延迟、浪费请求

**WebSocket / SSE**：服务端主动推送。
- 优点：实时、零浪费
- 缺点：要额外维护长连接，Nginx 配置复杂

**判断标准**：任务耗时几秒、用户能等 → 轮询；任务耗时几十秒且要显示进度 → SSE；需要双向通信 → WebSocket。

**为什么要限制轮询次数？** 防止后端挂了或任务永远卡住时，前端无限发请求把浏览器/服务器拖死。

### 13.7 Celery 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 一直 `PENDING` | worker 没启动 | 跑 `celery -A config worker -l info` |
| 一直 `PENDING` | 两边 Redis 库/密码不一致 | 对比 `.env` 和 worker 启动日志里的 broker URL |
| `NotRegistered` | `autodiscover_tasks` 没找到 | 确认任务在 `app/tasks.py`、app 已在 `INSTALLED_APPS` |
| worker 启动就崩 | macOS/Linux 上 prefork 池问题 | 加 `--pool=solo`（单进程，仅调试用） |
| 改了代码任务没变 | worker 是旧代码 | 重启 worker（生产用 `--autoreload` 仅开发） |
| 结果过一段时间消失 | `result_expires` 默认 1 天 | 正常；要更长就配 `CELERY_RESULT_EXPIRES` |
| 任务执行两次 | 任务不幂等 + 重试 | 任务设计成「重复执行结果一样」 |

### 13.8 什么时候不该用 Celery

- 任务只要 50ms：异步反而增加复杂度，直接同步做；
- 必须立刻告诉用户结果（比如登录校验）：不能用；
- 需要严格事务一致（扣库存 + 写订单）：要么放一个事务里同步做，要么用更可靠的消息方案（如 RabbitMQ + 事务消息 / 本地消息表）。

**Celery 保证「至少执行一次」，不保证「只执行一次」。** 所以任务必须幂等（重复跑不会产生重复数据）。

## 第 14 章 自定义管理命令：一条命令灌入演示数据

### 14.1 为什么不手动加数据

手动在 Admin 里点 16 次，每次重建环境都要重来，还容易漏。写成命令后：

```bash
python manage.py seed_demo
```

一条命令搞定，且可以写进 README、写进 CI。

### 14.2 目录结构必须精确

```
library/
└── management/
    ├── __init__.py          ← 必须有
    └── commands/
        ├── __init__.py      ← 必须有
        └── seed_demo.py     ← 文件名 = 命令名
```

**少一个 `__init__.py` 会怎样？** Python 不认这是包，`python manage.py seed_demo` 报 `Unknown command: 'seed_demo'`。

**命名规则**：文件名 `seed_demo.py` → 命令 `python manage.py seed_demo`。下划线保留，不要写成 `seed-demo`。

### 14.3 代码结构

```python
from django.core.management.base import BaseCommand

class Command(BaseCommand):
    help = "写入演示用的分类和图书数据（可重复执行）"

    def handle(self, *args, **options):
        # 干活的地方
        self.stdout.write(self.style.SUCCESS("完成"))
```

三个固定约定：

1. 类名必须叫 `Command`；
2. 必须继承 `BaseCommand`；
3. 逻辑写在 `handle()` 里。

`self.stdout.write` 而不是 `print` 的原因：可以被测试捕获、支持 `--verbosity` 控制、输出带颜色（`self.style.SUCCESS` 是绿色）。

### 14.4 `get_or_create` 与 `update_or_create`

```python
category, created = Category.objects.get_or_create(name=name)
```

| 返回值 | 含义 |
| --- | --- |
| `category` | 拿到或新建的对象 |
| `created` | `True` = 这次新建的，`False` = 原来就有 |

```python
Book.objects.update_or_create(
    title=title,                        # 查找条件
    defaults={                          # 找到就更新这些字段，没找到就连同条件一起创建
        "author": author,
        "price": Decimal(price),
        "stock": stock,
        "category": categories[category_name],
    },
)
```

**为什么用它们而不是 `create()`？**

`create()` 每次执行都插一条新数据，跑两次命令就变成 24 本书、分类报 `Duplicate entry '技术' for key 'name'`。

`get_or_create` / `update_or_create` 让命令**幂等**（执行 1 次和 100 次结果一样）。

**为什么分类用 `get_or_create`、图书用 `update_or_create`？**

- 分类：已存在就够用，不需要改（名称是查找键本身，没什么可改的）；
- 图书：已存在时希望把价格、库存刷新成最新演示值。

### 14.5 更完整的命令还能做什么

```python
def add_arguments(self, parser):
    parser.add_argument("--reset", action="store_true", help="先清空再导入")

def handle(self, *args, **options):
    if options["reset"]:
        Book.objects.all().delete()       # 注意：有 PROTECT 时分类删不掉，要先删书
        Category.objects.all().delete()
```

**为什么先删书再删分类？** 因为 `on_delete=PROTECT`。反过来的话删分类会抛 `ProtectedError`。

> 生产环境千万别写「一键清空」的命令，或者至少加 `--i-know-what-im-doing` 这种确认参数。

## 第 15 章 前端搭建：Vite + Vue 2.7

### 15.1 为什么是 Vue 2.7 而不是 Vue 3

用户要求 Vue 2。Vue 2 已于 2023-12-31 停止维护，但企业存量项目大量还在用。

**2.7 是 Vue 2 的最后一个版本**，它把 Vue 3 的 `<script setup>`、`defineComponent` 等能力反向移植了回来，是 Vue 2 里最值得学的版本。

**学习建议**：先把 2.7 的选项式 API（`data`/`methods`/`computed`）学透，再学 Vue 3 的组合式 API，迁移成本很小。

### 15.2 为什么不用 `npm create vite` 官方模板

因为官方 `vue` 模板生成的是 **Vue 3**。要做 Vue 2.7 项目，最省事的方式是**手写 4 个文件**：

```
frontend/
├── package.json          ← 声明依赖
├── vite.config.js        ← 开发服务器 + 代理
├── index.html            ← 页面入口
└── src/
    ├── main.js           ← 创建 Vue 实例
    ├── api.js            ← axios 封装
    └── App.vue           ← 页面组件
```

### 15.3 package.json 逐行

```json
{
  "name": "library-practice-frontend",
  "private": true,
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview"
  },
  "dependencies": {
    "axios": "^1.7.9",
    "vue": "2.7.16"
  },
  "devDependencies": {
    "@vitejs/plugin-vue2": "^2.3.3",
    "vite": "^5.4.11"
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `private: true` | 防止手滑 `npm publish` 发到公共仓库 |
| `scripts.dev` | `npm run dev` → 启动开发服务器 |
| `scripts.build` | 产出 `dist/` 静态文件，交给 Nginx |
| `dependencies` | 运行时要用的包 |
| `devDependencies` | 只在开发/构建时用（打包后不进产物） |
| `"vue": "2.7.16"` | **没有 `^`**，锁死版本。Vue 2 已停止更新，用精确版本避免意外 |
| `"vite": "^5.4.11"` | 有 `^`，允许 5.x 内小版本升级（修 bug） |

**`^` 是什么？** `^1.7.9` 允许装 `1.7.9` ~ `1.999.999`，但不允许 `2.0.0`（大版本可能不兼容）。

**`package-lock.json` 要不要提交 Git？** 要。它锁定每个依赖的精确版本和下载地址，保证「你装的和同事装的一模一样」。

### 15.5 index.html：为什么只有一个 div

```html
<!DOCTYPE html>
<html lang="zh-CN">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>图书管理练习</title>
  </head>
  <body>
    <div id="app"></div>
    <script type="module" src="/src/main.js"></script>
  </body>
</html>
```

这是**单页应用（SPA）**：整个网站的 HTML 只有一个空 `div`，所有内容由 JS 动态渲染。

**好处**：页面切换不刷新，体验像原生 App。
**代价**：首屏要下载 JS；SEO 差（搜索引擎抓不到内容）；需要额外配置 404 回退。

**为什么 `type="module"`？** Vite 用浏览器原生 ES Module 加载，开发时不做打包，所以启动极快（几百毫秒）。

### 15.6 main.js

```js
import Vue from 'vue'
import App from './App.vue'

Vue.config.productionTip = false

new Vue({
  render: (h) => h(App)
}).$mount('#app')
```

| 行 | 作用 |
| --- | --- |
| `Vue.config.productionTip = false` | 关掉控制台那句「You are running Vue in development mode」 |
| `render: (h) => h(App)` | 用 render 函数而不是 `template`，因为运行时版本不包含模板编译器 |
| `.$mount('#app')` | 把组件挂到 `index.html` 的 `<div id="app">` 上 |

**`h` 是什么？** 是 `createElement` 的缩写（hyperscript）。Vue 内部用它把组件描述成虚拟 DOM。

**为什么不用 `template: '<App/>'`？** 因为 Vite 里 `import Vue from 'vue'` 引入的是**运行时版本**（不含模板编译器），写 `template` 会报：

```
[Vue warn]: You are using the runtime-only build of Vue where the template compiler is not available.
```

用 `render` 函数就没这个问题，而且体积更小、性能更好。

### 15.7 api.js：统一封装 axios

```js
import axios from 'axios'

export const http = axios.create({
  baseURL: '/api',
  timeout: 10000
})
```

**为什么 `baseURL: '/api'` 而不是 `http://127.0.0.1:8001/api`？**

因为写完整地址会触发**跨域**（第 17 章详解）。写成相对路径 `/api`，浏览器会请求「当前页面的域名 + /api」，再由 Vite 代理转发。

**`timeout: 10000` 的意义**：默认 axios 永不超时。后端卡死时页面会一直转圈，用户以为坏了。10 秒放弃并报错，体验更好。

> 注意：异步报表接口是 202 立即返回的，不受 10 秒限制。但**轮询**的 GET 请求受限制，单次查询应该很快。

**以后要加登录 token，只改这一处**：

```js
http.interceptors.request.use((config) => {
  const token = localStorage.getItem('token')
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})
```

这就是「统一封装」的价值：不用在 20 个请求里各写一遍。

### 15.8 必须记住的 Vue 2 响应式陷阱

Vue 2 用 `Object.defineProperty` 实现响应式，它**只能监听初始化时已存在的属性**。

```js
data() {
  return { book: { title: '三体' } }
}

// ❌ 不触发视图更新
this.book.price = 68

// ✅ 用 $set
this.$set(this.book, 'price', 68)

// ✅ 删除属性也要用 $delete
this.$delete(this.book, 'price')
```

**数组也有坑**：

```js
// ❌ 不触发更新
this.books[0] = newBook
this.books.length = 0

// ✅
this.$set(this.books, 0, newBook)
this.books.splice(0)          // 清空
```

**为什么本项目没踩到？** 因为所有数据都是「整个替换」：

```js
this.books = data.results        // ✅ 替换整个引用，一定触发更新
this.categories = data           // ✅
this.form = { ... }              // ✅
```

**规则：优先整对象/整数组替换，别去改深层属性。** 这是最省心的写法。

> Vue 3 改用 `Proxy`，这两个坑都没了。这也是升级 Vue 3 的一大动力。

## 第 16 章 App.vue 逐块拆解

### 16.1 一个 .vue 文件的三段式

```vue
<template>
  <!-- 长什么样：HTML + 指令 -->
</template>

<script>
export default {
  // 什么逻辑：数据、方法、生命周期
}
</script>

<style>
/* 什么样式 */
</style>
```

**为什么能写在一个文件里？** 因为 `@vitejs/plugin-vue2` 会在构建时把它拆成 JS 模块（template 编译成 render 函数，style 抽出来）。

### 16.2 区块 1：服务状态

```vue
<button @click="loadHealth">刷新状态</button>
<pre>{{ healthText }}</pre>
```

```js
async loadHealth() {
  this.healthError = ''
  try {
    const { data } = await http.get('/health/')
    this.health = data
  } catch (err) {
    this.healthError = err.message
  }
},

computed: {
  healthText() {
    if (this.healthError) return `请求失败：${this.healthError}`
    if (!this.health) return '加载中...'
    return JSON.stringify(this.health, null, 2)
  }
}
```

**为什么用 `computed` 而不是在 `methods` 里拼字符串？**

`computed` 有缓存：依赖的 `health` / `healthError` 不变时不会重算。而且模板里直接写 `{{ healthText }}` 比 `{{ formatHealth() }}` 更清晰（方法每次渲染都会执行）。

**`JSON.stringify(x, null, 2)` 的 `null, 2` 是什么？**

- 第二个参数 `replacer`：`null` 表示不过滤字段；
- 第三个参数 `space`：缩进 2 空格，让 `<pre>` 里的 JSON 好看。

### 16.3 区块 2：分类 chips

```vue
<span v-for="c in categories" :key="c.id" class="chip">
  {{ c.name }}
  <b>{{ c.book_count }}</b>
  <button class="x" @click="removeCategory(c)">×</button>
</span>
```

**`:key` 为什么必须有？**

Vue 用 key 判断「哪个节点是哪个」。没有 key 时用「就地复用」策略：删掉第 1 个分类，Vue 可能把第 2 个的数据塞进第 1 个 DOM，导致动画错乱、输入框内容串位。

**`:key` 为什么用 `id` 不用 `index`？**

用 index 时，删除中间一项会导致后面所有项的 index 变化，Vue 会认为「所有项都变了」，白白重渲染，也可能复用错组件状态。

**`c.book_count` 从哪来？** 后端 `CategorySerializer` 的 `IntegerField(source="books.count")` 算出来的。

### 16.4 区块 3：行内编辑

这是本项目最值得学的一段。

```vue
<tr v-for="book in books" :key="book.id">
  <!-- 编辑态 -->
  <template v-if="editingId === book.id">
    <td><input v-model="editDraft.title" /></td>
    ...
    <button @click="saveEdit(book.id)">保存</button>
    <button class="ghost" @click="cancelEdit">取消</button>
  </template>

  <!-- 展示态 -->
  <template v-else>
    <td>{{ book.title }}</td>
    ...
    <button class="ghost" @click="startEdit(book)">编辑</button>
    <button class="danger" @click="removeBook(book)">删除</button>
  </template>
</tr>
```

```js
startEdit(book) {
  this.editingId = book.id
  this.editDraft = {
    title: book.title,
    author: book.author,
    price: Number(book.price),     // 字符串 "89.00" → 数字 89
    stock: book.stock,
    category: book.category
  }
},

cancelEdit() {
  this.editingId = null
}
```

**设计要点 1：为什么用「一个 `editingId` + 一个 `editDraft`」，而不是每行一个 `isEditing`？**

因为同一时刻只允许编辑一行。用 `editingId` 天然保证互斥：点第二行的编辑，第一行自动退出。如果每行一个布尔值，要额外写代码关掉其他行。

**设计要点 2：为什么要有 `editDraft`（草稿），不能直接 `v-model="book.title"`？**

如果直接绑定原对象：

```
用户改到一半 → 点取消 → 但 book.title 已经被改了 → 数据和后端不一致
```

有了草稿：取消 = 丢掉草稿，原对象没动过。这也是「可撤销」的基础。

**设计要点 3：为什么 `price` 要 `Number()`？**

后端返回的是字符串 `"89.00"`（`DecimalField` 的序列化结果）。`<input type="number" v-model.number>` 需要数字。不转的话，编辑时输入框可能显示为空或行为怪异。

**设计要点 4：为什么 `saveEdit` 用 PATCH 而不是 PUT？**

- `PUT` = 整体替换：没传的字段会被清空/重置
- `PATCH` = 局部更新：只改传的字段

前端只传 5 个可编辑字段，用 PATCH 语义更准确，也不怕漏传 `created_at` 之类。

### 16.5 搜索、筛选、分页的联动

```js
async loadBooks() {
  const { data } = await http.get('/books/', {
    params: {
      search: this.search || undefined,
      category: this.filterCategory || undefined,
      page: this.page
    }
  })
  this.books = data.results
  this.total = data.count

  if (this.page > this.totalPages) {
    this.page = this.totalPages
    this.loadBooks()
  }
},

doSearch() {
  this.page = 1          // ★ 关键
  this.loadBooks()
}
```

**为什么 `doSearch` 必须把 `page` 重置成 1？**

假设你在第 3 页（剩 2 条），然后搜索「三体」（只有 1 条）。如果还请求 `page=3`，后端返回 `count=1, results=[]`，页面显示「没有匹配的图书」——但其实是有的，只是不在第 3 页。

**这是新手最容易犯的分页 bug。**

**`this.search || undefined` 为什么不是 `this.search || ''`？**

axios 会把 `search=''` 拼成 `?search=`，Django 收到空字符串。虽然 `SearchFilter` 会忽略空值，但 URL 里多个 `&search=` 很脏，也不利于缓存 key 复用。

`undefined` 会让 axios **完全不拼这个参数**，URL 干净。

**同类问题还有 `filterCategory`**：初始值是 `''`（空字符串，代表「全部分类」），转成 `undefined` 后就不会发 `?category=`。

### 16.6 越界修正为什么放在 `loadBooks` 里

```js
if (this.page > this.totalPages) {
  this.page = this.totalPages
  this.loadBooks()
}
```

**这是递归调用吗？会不会死循环？**

是递归，但安全：

- 第 1 次：page=3，total=10 → totalPages=2 → 修正为 2 → 再请求
- 第 2 次：page=2，total=10 → totalPages=2 → `2 > 2` 为 false → 停

因为每次修正都会让 page **严格变小**，且 totalPages ≥ 1，所以最多递归几次就停。

> 更严谨的写法是 `if (this.page > this.totalPages && this.totalPages >= 1)`，但数学上 `Math.max(1, ...)` 已经保证 ≥ 1，所以不必重复判断。

### 16.7 `<select>` 的 `:value="null"`

```vue
<select v-model="form.category">
  <option :value="null">未分类</option>
  <option v-for="c in categories" :key="c.id" :value="c.id">{{ c.name }}</option>
</select>
```

**为什么 `:value="null"` 而不是 `value=""`？**

关键在于 `v-model` 绑定的 `category` 要传给后端。后端外键字段接受 `null`（未分类）。

- `value=""` → 提交 `category: ""` → DRF 报 `"“” 不是合法的主键值"`（400）
- `:value="null"` → 提交 `category: null` → 正确存为 NULL

**`：value` 前面的冒号**表示「这是 JS 表达式，不是字符串」。`value="null"` 会得到字符串 `"null"`，一样的错误。

### 16.8 轮询报表

```js
async runReport() {
  this.notice = ''
  this.reportRunning = true
  try {
    const { data } = await http.post('/tasks/report/')
    this.reportTask = { task_id: data.task_id, status: 'PENDING' }
    await this.pollReport(data.task_id)
  } catch (err) {
    this.showError(err)
  } finally {
    this.reportRunning = false
  }
},

async pollReport(taskId) {
  for (let i = 0; i < 12; i += 1) {
    await new Promise((resolve) => setTimeout(resolve, 700))
    const { data } = await http.get(`/tasks/${taskId}/`)
    this.reportTask = data
    if (data.status === 'SUCCESS' || data.status === 'FAILURE') return
  }
}
```

**`new Promise((resolve) => setTimeout(resolve, 700))` 是什么？**

`setTimeout` 是回调式 API，不能 `await`。用 Promise 包一层，就能写成「同步风格」的等待 700ms。这叫 **promisify**。

**为什么要先 `await` 再请求，而不是先请求再等？**

因为任务需要时间。刚提交就查一定是 `PENDING`，白白浪费一次请求。

**`finally` 为什么必要？**

无论成功、失败、还是抛异常，都要把按钮恢复成可点击。写在 `finally` 里才不会漏。

**如果超过 12 次还没完成会怎样？**

循环结束，`reportRunning` 变 false，页面显示最后一次查到的状态（大概率 `STARTED`）。用户可以再点一次按钮。这是「优雅降级」：不报错，让用户自己重试。

### 16.9 错误提示统一处理

```js
showError(err) {
  const detail = err && err.response && err.response.data
  if (detail && detail.detail) {
    this.notice = `操作失败：${detail.detail}`
  } else {
    this.notice = `操作失败：${err.message}`
  }
}
```

**为什么要一层层判断 `err && err.response && err.response.data`？**

axios 的错误有三种：

| 类型 | `err.response` | 场景 |
| --- | --- | --- |
| 服务器返回 4xx/5xx | 有 | 后端校验失败、500 |
| 请求超时 | 没有 | `timeout: 10000` 触发 |
| 网络断开 | 没有 | 后端没启动、断网 |

直接写 `err.response.data.detail` 会在后两种情况下抛 `TypeError: Cannot read property 'data' of undefined`，把真正的错误信息盖掉。

**为什么判断 `detail.detail`？**

DRF 的 `ValidationError({"detail": "..."})` 返回的结构是：

```json
{"detail": "该分类下还有图书，不能删除"}
```

而字段校验错误是：

```json
{"price": ["价格不能为负数"]}
```

本项目只在「分类删除失败」时用了 `detail` 这种结构，所以只处理这一种。**生产项目应该写一个完整的错误格式化函数**，把 `{字段: [错误列表]}` 也拼成中文提示。

前端页面能：新增分类 → 新增图书 → 搜索 → 筛选 → 翻页 → 行内编辑 → 删除 → 生成报表。

## 第 17 章 跨域与代理：为什么前端不直接请求 8001

### 17.1 同源策略

浏览器规定：**只有「协议 + 域名 + 端口」三者完全相同，才算同源。**

```
http://localhost:5174   （前端页面）
http://localhost:8001   （后端接口）

协议：http     = http      ✓
域名：localhost = localhost ✓
端口：5174     ≠ 8001      ✗   → 不同源！
```

不同源时，浏览器会拦截 `XMLHttpRequest` / `fetch` 的响应（注意：**请求已经发出去了，只是响应被藏起来**），控制台报：

```
Access to XMLHttpRequest at 'http://localhost:8001/api/books/'
from origin 'http://localhost:5174' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.
```

**为什么浏览器要这么设计？**

防止你正在逛的恶意网站偷偷用你的登录态（Cookie）去请求银行接口。同源策略是 Web 安全的地基。

**注意**：同源策略只约束**浏览器**。用 `curl`、Postman、后端服务互相调用都不受限制。所以「接口用 Postman 能通，浏览器不行」八成是跨域问题。

### 17.2 两种解决方案

**方案 A：CORS（后端允许）**

后端在响应头里加：

```
Access-Control-Allow-Origin: http://localhost:5174
Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
```

浏览器看到「后端明确允许了这个源」，就放行。

**方案 B：代理（前端绕开）**

让浏览器只访问 `localhost:5174`（同源），Vite 在**服务器端**把 `/api/*` 转发到 `localhost:8001`。

```
浏览器 → localhost:5174/api/books/       （同源，浏览器完全不管）
              ↓ Vite 服务器内部转发（不是浏览器行为，无同源限制）
         localhost:8001/api/books/
```

**本项目两个都配了**，但**平时走的是代理**，CORS 只是保险。

### 17.3 代理配置逐行

```js
export default defineConfig({
  plugins: [vue()],
  server: {
    port: 5174,
    proxy: {
      '/api': {
        target: 'http://127.0.0.1:8001',
        changeOrigin: true
      }
    }
  }
})
```

| 配置 | 作用 |
| --- | --- |
| `port: 5174` | 端口避开主项目的 5173 |
| `'/api'` | 匹配以 `/api` 开头的请求 |
| `target` | 转发到哪 |
| `changeOrigin: true` | 把请求头 `Host` 改成目标域名 |

**`changeOrigin` 到底改了什么？**

```
不加：Host: localhost:5174      ← 后端看到的还是前端域名
加：  Host: 127.0.0.1:8001      ← 后端以为请求是发给自己的
```

有些后端/网关会校验 `Host`，不改会返回 403/404。**加上它几乎没坏处，建议固定写 `true`。**

**为什么没有 `rewrite`？**

因为后端接口路径本身就带 `/api`（`config/urls.py` 里是 `path("api/", include("library.urls"))`）。

有 `rewrite` 的情况（后端路径不带 `/api`）：

```js
proxy: {
  '/api': {
    target: 'http://127.0.0.1:8001',
    changeOrigin: true,
    rewrite: (path) => path.replace(/^\/api/, '')   // /api/books/ → /books/
  }
}
```

**配错 `rewrite` 的典型症状**：前端 404，后端日志里路径少了一段。

### 17.4 生产环境怎么办

Vite 的 `proxy` **只在 `npm run dev` 时生效**。`npm run build` 打包出的 `dist/` 里没有代理。

生产环境用 Nginx：

```nginx
server {
    listen 80;
    server_name example.com;

    # 前端静态文件
    location / {
        root /var/www/library-frontend/dist;
        try_files $uri $uri/ /index.html;      # SPA 路由回退
    }

    # 接口转发
    location /api/ {
        proxy_pass http://127.0.0.1:8001/api/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

**`try_files ... /index.html` 为什么必要？**

SPA 里 `/books/3` 这种路径在服务器上不存在对应文件。不加这行，用户刷新页面会 404。加了的含义是「找不到文件就返回 index.html，让前端路由自己处理」。

**生产环境还需要 CORS 吗？** 不需要，因为前后端已经同域（都通过 Nginx 的 80 端口）。所以 `CORS_ALLOWED_ORIGINS` 只填开发地址，生产可以不配。

### 17.5 预检请求（OPTIONS）

对于「非简单请求」（比如带 `Content-Type: application/json` 的 POST，或带自定义头），浏览器会先发一个 `OPTIONS` 请求问「我能这么干吗」：

```
OPTIONS /api/books/
Origin: http://localhost:5174
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type
```

后端必须返回 200 + 允许的头，浏览器才会发真正的 POST。

**这解释了为什么 `CorsMiddleware` 要放在中间件最前面**：OPTIONS 请求要在被 CSRF 等中间件拦截前处理掉。

**调试技巧**：如果浏览器 Network 面板里只看到一个 `OPTIONS` 红色失败，没有真正的 POST，就是预检没过。

✅ **本章验收**

浏览器打开 `http://localhost:5174`，Network 面板里 `/api/books/` 的请求地址应是 `http://localhost:5174/api/books/`（不是 8001），状态 200。

```text
改了 tasks.py                              →  必须手动 Ctrl+C 重启 celery
```

### 19.1 快速索引

### 19.2 MySQL 连不上（2002 / 2003）

**完整报错长这样**：

```text
django.db.utils.OperationalError: (2002, "Can't connect to server on '127.0.0.1' (36)")
```

**排查顺序**（从外到内，一步都别跳）：

```bash
# ① 容器在跑吗？
docker ps --filter name=django-study-mysql

# ② 端口映射对吗？（要找 3307->3306）
docker port django-study-mysql

# ③ 容器内部 MySQL 活了吗？
docker exec django-study-mysql mysqladmin -uroot -p'Henhaoji@119' ping

# ④ 宿主机能不能连上？
mysql -h127.0.0.1 -P3307 -udjango -p'Henhaoji@119' -e 'select 1;'
```

哪一步失败就修哪一步：

- ① 空 → `docker start django-study-mysql`
- ② 显示 3306 → 说明容器创建时映射写错了，只能删了重建：`docker rm -f django-study-mysql` 后重新 `docker run ... -p 3307:3306`
- ③ 失败 → `docker logs --tail 100 django-study-mysql`，常见是数据目录权限或初始化没完成（刚建的容器要等 20~30 秒）
- ④ 失败但 ③ 成功 → 检查 `.env` 里的 `MYSQL_PORT`

> **为什么容器刚启动连不上？** MySQL 首次初始化要建系统表，期间端口是通的但拒绝连接。等日志出现 `ready for connections` 再连。

### 19.3 Access denied（1045）

```text
(1045, "Access denied for user 'django'@'%' (using password: YES)")
```

三种可能：

1. `.env` 里 `MYSQL_PASSWORD` 打错（注意 `Henhaoji@119` 的大小写和 `@`）
2. 用户 `django` 没被授权访问 `practice_db`
3. 连的是**旧的 MySQL 容器**（宿主机 3306 上那个 MariaDB）

判断方法：`mysql -h127.0.0.1 -P3307 ...` 能通，但 Django 不通 → 一定是 Django 读到了错的配置。检查：

```bash
cd practice/backend
python - <<'PY'
import os, django
os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings")
django.setup()
from django.conf import settings
print(settings.DATABASES["default"])
PY
```

把密码打印出来，和 `.env` 对一眼。**注意 `.env` 改了之后必须重启 `runserver`**，Django 不会重新读环境变量。

授权 SQL（在 root 下执行）：

```sql
GRANT ALL PRIVILEGES ON practice_db.* TO 'django'@'%';
FLUSH PRIVILEGES;
```

### 19.4 Unknown database（1049）

```text
(1049, "Unknown database 'practice_db'")
```

建库：

```sql
CREATE DATABASE practice_db
  DEFAULT CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;
```

> **`utf8mb4` 和 `utf8` 的区别**：MySQL 的 `utf8` 其实是「残缺版」，最多 3 字节，存不了 emoji。`utf8mb4` 才是真正的 UTF-8。**新建库一律用 `utf8mb4`。**

### 19.5 No module named 'django'

```text
ModuleNotFoundError: No module named 'django'
```

99% 是没激活 venv。看命令行前面有没有 `(.venv)`：

```bash
source .venv/bin/activate   # 在 practice/backend 目录下
which python                # 应该指向 practice/backend/.venv/bin/python
```

如果 `.venv` 目录根本不存在，重建：

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
```

### 19.6 No module named 'MySQLdb'

```text
django.core.exceptions.ImproperlyConfigured: Error loading MySQLdb module.
Did you install mysqlclient?
```

Django 默认要 `mysqlclient`，我们用的是 `PyMySQL`（纯 Python，不用编译）。但要**骗 Django 说自己是 MySQLdb**，靠的是 `config/__init__.py` 里这两行：

```python
import pymysql

pymysql.install_as_MySQLdb()
```

排查：

1. `pip show PyMySQL` 有没有装
2. `config/__init__.py` 里这两行在不在
3. **这两行必须在任何 Django 模块导入之前执行**——放在 `config/__init__.py` 最顶部就是干这个的

### 19.7 表不存在 / 有未执行的迁移

```text
You have 3 unapplied migration(s). Your project may not work properly...
```

或者：

```text
(1146, "Table 'practice_db.library_book' doesn't exist")
```

```bash
python manage.py showmigrations library   # 看 [ ] 还是 [X]
python manage.py migrate                  # 补上
```

如果 `showmigrations` 显示已应用但表还是不存在，说明**迁移文件和数据库对不上**（常见于手动改过库、或者删了迁移文件）。开发环境可以重置：

```bash
# ⚠️ 会清空 practice_db 的所有数据，只在开发环境用
python manage.py migrate library zero     # 回滚 library 的所有迁移
python manage.py migrate                  # 重新建表
python manage.py seed_demo                # 重新灌数据
```

### 19.8 密码里的 @ 导致连接串解析错

这是本项目踩过的真实坑。Redis 连接串格式是：

```text
redis://:密码@主机:端口/库号
```

密码里本身有 `@`（`Henhaoji@119`），解析器会把**第一个 `@` 当成密码和主机的分隔符**，于是把 `119@127.0.0.1` 当成主机名，报认证或 DNS 错误。

**解决：URL 里的特殊字符要百分号编码**，`@` → `%40`：

```dotenv
REDIS_CACHE_URL=redis://:Henhaoji%40119@127.0.0.1:6380/2
REDIS_URL=redis://:Henhaoji%40119@127.0.0.1:6380/3
```

注意：**只有 URL 形式需要编码**。像 `MYSQL_PASSWORD=Henhaoji@119` 这种独立字段是原样传的，不用编码。

其他常见编码：`#` → `%23`、`/` → `%2F`、`:` → `%3A`、空格 → `%20`。

### 19.9 CORS 报错

浏览器控制台：

```text
Access to XMLHttpRequest at 'http://127.0.0.1:8001/api/books/' from origin
'http://localhost:5174' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.
```

说明前端**直接请求了 8001**（绕过了代理），而后端白名单里没有这个 origin。

两种修法（选一种，推荐第一种）：

1. **走 Vite 代理**（本项目用的）：`axios` 的 `baseURL` 写 `/api`，请求地址就变成 `localhost:5174/api/...`，同源，根本没有跨域。
2. **后端加白名单**：

```python
CORS_ALLOWED_ORIGINS = [
    "http://localhost:5174",
    "http://127.0.0.1:5174",
]
```

> 注意 `localhost` 和 `127.0.0.1` 在浏览器眼里是**两个不同的 origin**，两个都要写。

### 19.10 前端 404，但 curl 后端正常

这是「代理问题」的典型特征。

**排查三步**：

1. 浏览器 Network 面板看请求 URL：
   - 是 `localhost:5174/api/books/` → 代理配了，但转发后 404 → 看第 2 步
   - 是 `127.0.0.1:8001/api/books/` → 根本没走代理 → 查 `baseURL`
2. 看后端终端有没有收到请求：
   - **没收到** → 代理没生效（改了 `vite.config.js` 必须重启 `npm run dev`）
   - 收到但 404 → 路径不对，看第 3 步
3. 对比路径：

```text
后端路由：/api/ + books/     = /api/books/
前端请求：baseURL '/api' + '/books/' = /api/books/   ✅
如果 baseURL 写成 '/api/' 再加 '/books/' → /api//books/  ❌ 双斜杠
```

> **改 `vite.config.js` 一定要重启 dev server**，它不像 `App.vue` 那样热更新。

### 19.12 删除分类报 ProtectedError

```text
ProtectedError: ("Cannot delete some instances of model 'Category' because they
are referenced through protected foreign keys: 'Book.category'.", ...)
```

这不是 bug，是**设计如此**。`on_delete=PROTECT` 的作用就是防止「分类删了、书变成孤儿」。

本项目在 `CategoryViewSet.perform_destroy` 里把它翻译成了友好的 400：

```python
try:
    instance.delete()
except ProtectedError:
    raise ValidationError({"detail": "该分类下还有图书，不能删除"})
```

**为什么会看到原始 `ProtectedError`？** 说明异常没被捕获——检查是不是在别的地方（比如 admin 后台、shell）删的。admin 后台删除会弹出 Django 自带的确认页，那里会列出关联对象。

想要「删分类时把书也删掉」怎么办？把 `on_delete` 改成 `CASCADE`。**但这是危险操作**，真实项目里通常不允许。

### 19.13 Celery 任务一直 PENDING

**这是最高频的坑**，按顺序查：

```text
① worker 起了吗？
   ps aux | grep 'celery -A config'
   没有 → 启动它

② worker 和后端连的是同一个 broker 吗？
   都读 .env 里的 REDIS_URL（3 号库）
   看 redis：docker exec ... -n 3 --scan
   如果后端写到了 0 号库、worker 读 3 号库 → 永远收不到

③ 任务名对得上吗？
   worker 启动日志里 [tasks] 列表有没有 generate_stock_report
   没有 → autodiscover_tasks 没找到，检查 library/tasks.py

④ worker 是旧进程吗？
   改了 tasks.py 但没重启 → Ctrl+C 重启 worker

⑤ 任务执行时报错了吗？
   docker exec ... -n 3 get celery-task-meta-<task_id>
   或者看 worker 终端里的红色 traceback
```

**`Received unregistered task of type ...` 的完整含义**：worker 收到了消息，但自己的任务注册表里没有这个名字。原因通常是：

- 改过任务函数名/模块路径，但没重启 worker
- worker 启动时 `INSTALLED_APPS` 里没有 `library`

**怎么确认任务真的写进队列了？**

```bash
# 3 号库（Celery）
docker exec django-study-redis redis-cli -a 'Henhaoji@119' --no-auth-warning -n 3 --scan --pattern 'celery*'
```

正常情况下能看到 `celery`（队列 list）和 `celery-task-meta-<uuid>`（任务结果）。如果队列里堆了很多条而 worker 没消费，就是 worker 没起或者连错库。

### 19.14 dict() 用在列表上

```text
ValueError: dictionary update sequence element #0 has length 4; 2 is required
```

这是本项目写缓存时真实踩的坑。原本想「复制一份再缓存」：

```python
cache.set(key, dict(response.data), timeout=30)   # ❌
```

但 `response.data` 在**分页时是 dict**（有 `count/results`），在 **`pagination_class = None` 时是 list**。`dict(list)` 会试图把列表每项当成 `(key, value)` 二元组，于是报错（第一项有 4 个元素）。

正确做法：**原样存**。

```python
cache.set(key, response.data, timeout=30)         # ✅
```

> 教训：**类型不确定时不要做「看起来更安全」的转换**。`response.data` 本身就是可 JSON 序列化的结构，Django 的 Redis 缓存会自己序列化。

### 19.15 路由顺序导致 'report' 被当成 task_id

```text
ValueError: Field 'id' expected a number but got 'report'.
```

因为 `tasks/<str:task_id>/` 写在 `tasks/report/` 前面时，`report` 会被 `<str:task_id>` 匹配走，然后拿去查数据库主键。

Django 的 URL 匹配是**从上到下、先匹配先赢**，不是「最精确优先」。所以：

```python
urlpatterns = [
    path("tasks/report/", StockReportTaskView.as_view()),   # 具体路径在前
    path("tasks/<str:task_id>/", TaskStatusView.as_view()),  # 变量路径在后
]
```

同理，`DefaultRouter` 生成的路由也建议放在自定义 `path` **后面**，避免通配吃掉具体路径。

### 19.16 分页页码越界

场景：你在第 3 页，删光了这一页的数据，再刷新列表——`count` 变小，`page=3` 已经超出范围，DRF 返回：

```json
{"detail": "Invalid page."}
```

本项目的处理（`App.vue` 的 `loadBooks`）：

```js
this.total = data.count
if (this.page > this.totalPages) {
  this.page = this.totalPages
  this.loadBooks()      // 自动回退到最后一页再拉一次
}
```

> 为什么要在**前端**处理？因为后端不知道用户「原来在第几页」。也有另一种做法：后端对越界页码返回最后一页而不是 404，但那会掩盖前端的状态错误，不推荐。

### 19.17 前端白屏 / 只有 HTML 没内容

按 F12 看 Console：

| 报错 | 原因 | 修法 |
| --- | --- | --- |
| `Failed to resolve component: ...` | 组件没注册 | 检查 `components` 或 import |
| `Cannot read properties of undefined (reading 'xxx')` | 数据还没到就渲染 | 加 `v-if` 或用默认值 |
| 页面完全空白且无报错 | `index.html` 里的挂载点 id 和 `main.js` 不一致 | 都改成 `#app` |
| `Uncaught SyntaxError` | 浏览器缓存了旧文件 | 硬刷新 `Ctrl+Shift+R` |

本项目 `main.js` 用的是 render 函数而不是 template：

```js
new Vue({
  render: (h) => h(App),
}).$mount('#app')
```

> **为什么不用 `template: '<App/>'`？** 因为项目里没有引入 Vue 的**完整版**（带编译器），只有运行时版。`template` 需要运行时编译，会报「You are using the runtime-only build」。`render` 函数不需要编译，所以永远可用。

### 19.18 排查问题的通用套路

遇到没见过的错，按这个顺序，**不要跳步**：

```text
1. 读报错的最后一行（Python 的异常类型和信息在最后）
2. 读报错的第一行（哪个文件、哪一行触发的）
3. 判断层级：
   连不上数据库/Redis      → 基础设施层
   ImportError/配置错      → 环境层
   404/401/400             → 路由/接口层
   500 + traceback         → 代码层
   前端白屏/样式错          → 前端层
4. 用最小手段隔离：
   curl 测后端 → 排除前端
   python manage.py shell 测 ORM → 排除接口层
   mysql 命令行测连接 → 排除 Django
5. 一次只改一个地方，改完立刻验证
```

✅ **本章验收**：随便制造一个错误（比如把 `.env` 里端口改成 3308），用上面的套路在 3 分钟内定位到原因，再改回来。

## 第 21 章 拓展练习（带思路，不给答案）

这一章的练习都**基于现有项目改造**。每题给出目标、思路、涉及知识点、验收标准，但**不贴完整代码**——自己写出来的才是你的。

### 21.1 后端篇

#### 练习 1：给 Book 加一个「出版日期」

**目标**：新增 `published_at = models.DateField(null=True, blank=True)`，并让接口能返回它。

**思路**：

1. 改 `models.py` → `makemigrations` → `migrate`
2. 因为允许为空，迁移时不会要求填默认值
3. `serializers.py` 的 `fields` 里加上这个字段（用 `"__all__"` 的话自动就有）
4. admin 的 `list_display` 里加上，方便看

**涉及知识点**：`DateField` 与 `DateTimeField` 的区别、可空字段的迁移、`auto_now_add` 只能用于 `DateTimeField`

**验收**：`curl /api/books/1/` 返回里有 `published_at`，值为 `null` 或日期字符串

**常见坑**：`DateField` 不能用 `auto_now_add`（那是 `DateTimeField` 专属）；如果加字段时没写 `null=True`，`makemigrations` 会交互式问你默认值，卡住终端

---

#### 练习 2：按价格区间筛选

**目标**：`GET /api/books/?min_price=20&max_price=50` 只返回这个区间的书。

**思路**：

1. 在 `BookViewSet.get_queryset` 里读 `self.request.query_params`
2. 用 `queryset.filter(price__gte=..., price__lte=...)`
3. 注意参数可能没传、可能不是数字
4. 参考现有 `category` 参数的写法：`try/except (TypeError, ValueError)`

**涉及知识点**：`__gte` / `__lte` 查询、`query_params`、参数校验、`queryset.none()`

**验收**：`?min_price=20&max_price=50` 的结果里每本书价格都在区间内；传 `?min_price=abc` 不报 500

**常见坑**：`DecimalField` 比较时传字符串也能工作，但最好显式 `Decimal(...)`；不要用 `price >= min_price` 这种 Python 写法，那是内存里过滤

---

#### 练习 3：给图书加「库存预警」

**目标**：`GET /api/books/?low_stock=1` 返回库存 < 5 的书。

**思路**：

1. 同样在 `get_queryset` 里加参数判断
2. `filter(stock__lt=5)`
3. 想更进一步：把阈值做成参数 `?low_stock=10`

**涉及知识点**：`__lt` / `__gt`、布尔型 query 参数（字符串 `"1"` 怎么判断）

**验收**：结果里所有书 `stock < 5`

**常见坑**：query 参数永远是**字符串**，`if low_stock:` 对 `"0"` 也是真，要写 `if low_stock == "1"`

---

#### 练习 4：分类列表按图书数量排序

**目标**：`/api/categories/` 支持 `?ordering=-book_count`。

**思路**：

1. 现在 `book_count` 是 `Serializer` 里算的，**不能直接用于数据库排序**
2. 用 `annotate(book_count=Count("books"))` 在查询集上算
3. 注意 `CategoryViewSet` 目前 `pagination_class = None`，`ordering_fields` 已有
4. 加完后可以去掉 Serializer 里的 `book_count`，避免重复

**涉及知识点**：`annotate` + `Count`、聚合与序列化的区别、`ordering_fields`

**验收**：`?ordering=-book_count` 时书最多的分类排第一

**常见坑**：`Count` 要 `from django.db.models import Count`；如果同时 `filter` 和 `annotate`，要注意顺序影响统计结果

---

#### 练习 5：批量导入图书

**目标**：写一个 `import_books` 管理命令，从 CSV 导入图书。

**思路**：

1. 复制 `seed_demo.py` 的结构
2. `add_argument("csv_path")` 接收文件路径
3. `csv.DictReader` 逐行读
4. 用 `update_or_create(title=..., defaults={...})` 保证幂等
5. 统计「新建 N 条、更新 M 条」并打印

**涉及知识点**：`argparse`（Django 命令用的就是它）、`csv` 模块、`update_or_create`、事务

**验收**：同一个 CSV 导入两次，数据条数不变

### A.3 写操作的 body 示例

**新建图书**：

```json
{
  "title": "流畅的 Python",
  "author": "Luciano Ramalho",
  "price": "109.00",
  "stock": 8,
  "category": 1
}
```

**局部更新（PATCH）**——只传要改的字段：

```json

```

**为什么前端编辑用 PATCH 而不是 PUT？** PUT 是「全量替换」，没传的字段会被当成空值；PATCH 是「局部更新」，只改传过去的字段。行内编辑只改了价格，用 PATCH 最安全。

```json

  "price": ["价格必须大于 0"],
  "stock": ["库存不能为负数"]
}
```

这些错误来自 `BookSerializer.validate_price` / `validate_stock`。

## 附录 B 数据库表结构

库名：`practice_db`，字符集 `utf8mb4`。

### B.1 `library_category`（分类表）

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | bigint | PK, AUTO_INCREMENT | 主键 |
| `name` | varchar(50) | NOT NULL, UNIQUE | 分类名，唯一索引 |
| `created_at` | datetime(6) | NOT NULL | 创建时间，自动写入 |

对应的 Django 模型：

```python
class Category(models.Model):

```

**为什么 `created_at` 是 `datetime(6)`？** Django 4.2 默认用微秒精度（6 位小数），所以是 `datetime(6)` 而不是 `datetime`。

### B.2 `library_book`（图书表）

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | bigint | PK, AUTO_INCREMENT | 主键 |
| `title` | varchar(120) | NOT NULL | 书名 |
| `author` | varchar(80) | NOT NULL | 作者（`blank=True` 只影响表单，数据库仍 NOT NULL，存空字符串） |
| `price` | decimal(8,2) | NOT NULL | 价格，最多 8 位、2 位小数 |
| `stock` | int unsigned | NOT NULL | 库存，不能为负 |
| `category_id` | bigint | NULL, FK → `library_category.id` | 所属分类，可为空 |
| `created_at` | datetime(6) | NOT NULL | 创建时间 |

**外键在数据库里的名字是 `category_id`**，不是 `category`。Django 在 Python 层叫 `book.category`（返回对象），在数据库层存 `category_id`（存数字）。这个区别在写原生 SQL 时很重要。

### B.3 索引与约束

| 名称 | 类型 | 作用 |
| --- | --- | --- |
| `PRIMARY` | 主键索引 | `id` |
| `library_category_name_..._uniq` | 唯一索引 | 保证分类名不重复 |
| `library_book_category_id_..._fk` | 外键约束 | 保证 `category_id` 指向真实分类 |
| `library_book_category_id_...` | 普通索引 | 加速 `WHERE category_id = ?` |

> **外键为什么自动建索引？** 因为「按分类查书」是最常见的查询（本项目 `?category=1` 就是），没有索引会全表扫描。

### B.4 常用查询

```sql
-- 每个分类有多少本书
SELECT c.id, c.name, COUNT(b.id) AS book_count
FROM library_category c
LEFT JOIN library_book b ON b.category_id = c.id
GROUP BY c.id, c.name;

-- 库存总价值
SELECT SUM(stock * price) AS total_value FROM library_book;

-- 没分类的书
SELECT * FROM library_book WHERE category_id IS NULL;

-- 价格最高的 5 本
SELECT title, price FROM library_book ORDER BY price DESC LIMIT 5;
```

> 最后一条对应 Django 的 `Book.objects.order_by("-price")[:5]`。**切片会自动加 `LIMIT`**，不会把全表读进内存。

## 附录 C Redis 里到底存了什么

本项目 Redis 用**两个不同的库**，避免互相干扰：

| 库号 | 用途 | 配置项 |
| --- | --- | --- |
| `0` | 空着（预留） | — |
| `2` | Django 缓存 | `REDIS_CACHE_URL=.../2` |
| `3` | Celery 队列 + 结果 | `REDIS_URL=.../3` |

> **为什么要分库？** 如果缓存和任务队列混在一起，`FLUSHDB` 清缓存会把没执行的任务一起删掉；排查时也容易把任务 key 当成缓存 key。

### C.1 缓存库（2 号）里有什么

实测扫出来的 key：

```text
:1:library:cache_version
:1:library:books:1794138138652060783:/api/books/?page=1
:1:library:categories:1794138138652060783:/api/categories/
:1:library:health
```

逐个解释：

| Key | 谁写的 | TTL | 含义 |
| --- | --- | --- | --- |
| `:1:library:cache_version` | `get_cache_version()` | 永久 | 缓存版本号（纳秒时间戳），一变所有列表缓存自动失效 |
| `:1:library:books:<版本>:<完整路径>` | `CachedListMixin.list` | 30 秒 | 某一页图书列表的响应数据 |
| `:1:library:categories:<版本>:<完整路径>` | `CachedListMixin.list` | 30 秒 | 分类列表的响应数据 |
| `:1:library:health` | `HealthView` | 10 秒 | 健康检查时写进去的探针值 |

**开头的 `:1:` 是什么？** 这是 Django 缓存框架自动加的 `KEY_PREFIX` + `version`。默认 `KEY_PREFIX=""`、`version=1`，拼起来就是 `:1:`。它让你可以在同一个 Redis 库里区分多个项目/环境。

**为什么 key 里带完整路径？** 因为列表接口有很多变体：

```text
/api/books/?page=1
/api/books/?page=2
/api/books/?search=Python
/api/books/?category=1&page=1
```

每个查询串的结果不一样，必须用完整路径做 key，否则第 2 页会读到第 1 页的缓存。

### C.2 怎么验证缓存真的生效

```bash
# 第一次请求（会写缓存）
curl -s 'http://127.0.0.1:8001/api/books/?page=1' > /dev/null

# 看 key 和 TTL
docker exec django-study-redis redis-cli -a 'Henhaoji@119' --no-auth-warning -n 2 --scan --pattern '*books*'
docker exec django-study-redis redis-cli -a 'Henhaoji@119' --no-auth-warning -n 2 ttl ':1:library:books:...'
```

`ttl` 应该返回 0~30 之间的数字。**返回 `-1` 表示永不过期**（那就不对了，检查 `LIST_CACHE_TIMEOUT`），**返回 `-2` 表示 key 不存在**（可能已经过期）。

再看响应头（本项目没加自定义头，所以用响应时间判断）：

```bash
time curl -s 'http://127.0.0.1:8001/api/books/?page=1' > /dev/null
time curl -s 'http://127.0.0.1:8001/api/books/?page=1' > /dev/null
```

第二次通常明显更快（几毫秒），因为它直接读 Redis，没查 MySQL。

### C.3 版本号缓存的失效过程

```text
初始：cache_version = 100

GET /api/books/?page=1
  key = library:books:100:/api/books/?page=1   → 未命中 → 查库 → 写入

POST /api/books/（新增一本书）
  perform_create → bump_cache_version()
  cache_version = 200

GET /api/books/?page=1
  key = library:books:200:/api/books/?page=1   → 未命中（新 key）→ 查库 → 写入最新数据
```

旧的 `:100:` 那些 key 没人再访问，30 秒后自动过期。**不需要遍历删除**，这就是版本号方案最大的好处。

**为什么不直接 `cache.delete()`？** 因为你根本不知道「这一个写操作会影响哪些缓存 key」。

举例：新增一本书，受影响的有：

```text
/api/books/?page=1
/api/books/?page=2
/api/books/?search=Python
/api/books/?category=1&page=1
/api/books/?ordering=-price
...
```

页数、搜索词、筛选条件、排序方式**任意组合**，key 的数量是无穷的。想精确删除，就得遍历所有 key 做模式匹配——而 `KEYS` / `SCAN` + 批量 `DEL` 在数据量大时既慢又容易漏。

**版本号方案把「删除 N 个 key」简化成了「改 1 个值」**：旧 key 不再被访问，30 秒后自然过期，Redis 的 TTL 机制帮你回收。这就是它比「精确删除」更实用的原因。

**代价是什么？** 写操作后的 30 秒内，旧 key 还占着内存（但不会被读到）。对练习项目完全无所谓；对内存敏感的场景可以调小 TTL。

### C.4 Celery 库（3 号）里有什么

先说明一个**很容易踩的坑**：Celery 用哪个库，完全由 `.env` 里的 `REDIS_URL` 决定：

```dotenv
REDIS_URL=redis://:Henhaoji%40119@127.0.0.1:6380/3
```

结尾那个 `/3` 就是「3 号库」。如果你忘了写 `/3`（或者旧的进程还在用默认配置），Celery 会**默认落到 0 号库**。这时候 `-n 3` 扫不到任何 key，你会以为 worker 挂了，其实它一直在，只是写进了 0 号库。

用下面这条命令一查就知道：

```bash
for i in 0 1 2 3; do echo -n "db$i: "; docker exec django-study-redis redis-cli -a 'Henhaoji@119' --no-auth-warning -n $i dbsize; done
```

本项目正常运行时应该是：`db0: 0`（或少量残留）、`db1: 0`、`db2: 1~几条`（缓存）、`db3: 几条`（Celery）。**0 号库的 `celery-task-meta-*` 就是历史残留**，可以直接 `-n 0 FLUSHDB` 清掉（前提是确认 0 号库没有别的东西）。

实测在 **3 号库**扫出来的 key：

```text
_kombu.binding.celery
_kombu.binding_deadlines
_kombu.binding_permanent.celery
_kombu.binding.celeryev
_kombu.binding.celery.pidbox
celery-task-meta-0cf589a4-ddb0-4096-bc8a-9b5e94ee8fbb
```

| Key | 作用 | 什么时候出现 |
| --- | --- | --- |
| `_kombu.binding.celery` | 队列与 exchange 的绑定关系（Celery 的「路由表」） | worker 启动后 |
| `_kombu.binding_deadlines` | 延迟任务（ETA / countdown）的索引 | 有延迟任务时 |
| `_kombu.binding_permanent.celery` | 持久化队列的绑定 | worker 启动后 |
| `celery-task-meta-<uuid>` | 任务结果（状态 + 返回值） | 任务执行完 |

**`celery-task-meta-*` 里存的是什么？** 本质是一个 JSON 字符串：

```json
{"status": "SUCCESS", "result": {"total_titles": 12, "total_stock": 108, "total_value": "7475.20"}, "traceback": null, "children": [], "date_done": "2026-11-08T19:40:00.123456"}
```

Django 里的 `AsyncResult(task_id).state` 和 `.result` 读的就是它。

**它什么时候消失？** 默认 `result_expires=86400`（24 小时）。过期后 `AsyncResult.state` 会永远返回 `PENDING`——**注意：`PENDING` 不等于「还在排队」，也可能表示「结果记录不存在或已过期」**。这是 Celery 新手最容易误解的一点。想区分「真的没跑」和「结果过期」，只能看 worker 日志。

**`_kombu.binding.*` 能删吗？** 不建议手动删。它们是 Celery 自动维护的元数据，删了可能导致 worker 收不到任务。要清队列用 `celery -A config purge`。

### C.5 Redis 排查命令速查

```bash
# 进 2 号库（缓存）
docker exec -it django-study-redis redis-cli -a 'Henhaoji@119' --no-auth-warning -n 2

# 进 3 号库（Celery）
docker exec -it django-study-redis redis-cli -a 'Henhaoji@119' --no-auth-warning -n 3
```

进去之后常用：

| 命令 | 作用 | 注意 |
| --- | --- | --- |
| `SCAN 0 MATCH library:* COUNT 100` | 分批扫 key | 比 `KEYS *` 安全 |
| `GET <key>` | 取值 | 缓存值是 JSON |
| `TTL <key>` | 剩余秒数 | `-1` 永久，`-2` 不存在 |
| `DBSIZE` | 当前库 key 总数 | |
| `TYPE <key>` | 看类型 | string / list / zset |
| `INFO memory` | 内存占用 | |
| `MONITOR` | 实时打印所有命令 | 调试完记得 `Ctrl+C` |
| `FLUSHDB` | 清空**当前库** | 别在 3 号库手抖 |

**`MONITOR` 的用法**：开一个终端跑 `MONITOR`，另一个终端刷新前端页面，就能看到 Django 发给 Redis 的每一条 `GET` / `SET`。判断「缓存到底有没有命中」最直观：

```text
# 第一次刷新（未命中）
"GET" ":1:library:books:179...:/api/books/?page=1"     ← 返回 nil
"SET" ":1:library:books:179...:/api/books/?page=1" ...

# 第二次刷新（命中）
"GET" ":1:library:books:179...:/api/books/?page=1"     ← 返回数据，后面没有 SET
```

**`KEYS *` 为什么危险？** Redis 是单线程的，`KEYS` 会一次性遍历所有 key 并阻塞其他命令。生产环境数据量大时，一次 `KEYS *` 可能卡住几秒，所有请求超时。**练习环境随便用，生产环境用 `SCAN`。**

## 结语：接下来怎么练

到这里，整套项目从「环境」到「代码」到「排错」都覆盖完了。

学习顺序建议：

1. **先跑通**：照第 18 章五步，把服务全起起来，浏览器点一遍。
2. **再拆解**：挑一个接口，从「前端点击」跟到「SQL 执行」，把整条链路画出来。

4. **最后从零重建**：照第 20 章清单，把 `practice/` 换个名字重建一次，不看代码只看清单。

三条最重要的心法：

- **官网永远比教程准**：Django / DRF / Celery / Vue 2 的官方文档都有中文或英文版，遇到版本相关问题优先查官网。
- **报错先看最后一行**：Python 的异常类型和信息在 traceback 最末尾，第一行只是「从哪开始」。
- **一次只改一个变量**：改配置、改代码、重启服务，一次只动一样，出问题才能立刻定位。
