## 二、这个项目由哪些东西组成

这套环境一共 **2 个容器 + 6 个本地进程**：

```
                    ┌─────────────────────────────────────────┐
  浏览器 ──────────►│  Vite 5173 (project1 前端)               │
                    │  Vite 5174 (practice 前端)               │
                    └───────────────┬─────────────────────────┘
                                    │ /api 代理
                                    ▼
                    ┌─────────────────────────────────────────┐
                    │  Django 8000 (project1)                  │
                    │  Django 8001 (practice)                  │
                    └───────┬─────────────────────┬───────────┘
                            │                     │ .delay() 投递任务
                            ▼                     ▼
                    ┌───────────────┐   ┌──────────────────────┐
                    │ MySQL :3307   │   │ Redis :6380           │
                    │ (Docker)      │   │ (Docker, 缓存 + 队列) │
                    └───────────────┘   └──────────┬───────────┘
                                                   │ 取任务
                                    ┌──────────────▼───────────┐
                                    │ Celery worker × 2         │
                                    │ (project1 / practice)     │
                                    └──────────────────────────┘
```

| 组件 | 是什么 | 端口 | 不启动会怎样 |
| --- | --- | --- | --- |
| `django-study-mysql` | MySQL 8.4 容器 | 宿主机 3307 | 后端一启动就报连不上数据库 |
| `django-study-redis` | Redis 8 容器 | 宿主机 6380 | 缓存接口报错，异步任务无法投递 |
| backend | project1 的 Django | 8000 | 5173 的页面所有接口 502/连接失败 |
| celery | project1 的 worker | 无 | 任务一直 `PENDING`（不是失败，是没人干） |
| frontend | project1 的 Vite | 5173 | 没有页面可看 |
| practice-backend | practice 的 Django | 8001 | 5174 的页面所有接口失败 |
| practice-celery | practice 的 worker | 无 | 库存报表任务一直 `PENDING` |
| practice-frontend | practice 的 Vite | 5174 | 没有页面可看 |

**关键认知：** Celery 的「生产者」是 Django 进程，「消费者」是 worker 进程，两者之间靠 Redis 传话。所以 **Django、worker、Redis 三个都得在**，缺一个任务就卡住。

## 三、`dev.sh` 脚本说明

脚本就在仓库根目录：[dev.sh](file:///home/gyc/Labs/Django-Study/dev.sh)。

### 3.1 命令

| 命令 | 作用 |
| --- | --- |
| `./dev.sh start` | 按依赖顺序启动：容器 → 两个 Django → 两个 Celery → 两个 Vite |
| `./dev.sh stop` | 逆序停止：Vite → Celery → Django → 容器 |
| `./dev.sh restart` | 等价于 `stop` + `start` |
| `./dev.sh status` | 列出容器状态、进程 pid、端口监听、`/api/health/` 结果 |
| `./dev.sh logs <服务名>` | `tail -f` 跟踪某个服务的日志 |

服务名固定为下面 6 个：

```
backend  celery  frontend  practice-backend  practice-celery  practice-frontend
```

例如：

```bash
./dev.sh logs celery            # 看 project1 的 worker 在干什么
./dev.sh logs practice-backend  # 看 practice 后端的报错
```

### 3.2 脚本把文件放在哪

| 路径 | 内容 | 是否进 Git |
| --- | --- | --- |
| `.run/<服务名>.pid` | 进程号 | 否（已在 `.gitignore`） |
| `logs/<服务名>.log` | 标准输出 + 标准错误 | 否（已在 `.gitignore`） |

### 3.3 启动时脚本具体做了什么

1. 检查 `docker`、`npm`、两个 `.venv`、两个 `node_modules` 是否存在，缺了直接告诉你缺什么，不会带着半套环境乱跑；
2. `docker start` 两个容器，然后**等端口真正可连**（MySQL 最多 60 秒）才继续——MySQL 容器「启动」和「能接受连接」中间差好几秒，不等就会偶发连库失败；
3. 依次启动 6 个进程，每个都做「进程还活着 + 端口已监听」双重确认；
4. 打印 `status`，并请求两个 `/api/health/` 确认 MySQL 和 Redis 都通。

### 3.4 脚本不会替你做的事

- **不会自动建库、不会自动迁移**。换新数据库时要手动 `migrate`（见 5.4）；
- **不会修改 Docker 的 restart policy**。容器仍然是 `--restart=no`，机器重启后需要你手动 `./dev.sh start`；
- **不会杀死不是它启动的进程**。停止前会校验 pid 对应的命令行，防止 pid 被系统复用后误杀别的程序。

### 5.4 创建 Docker 容器

**只有容器不存在时才需要执行。** 先确认：

```bash
docker ps -a --format '{{.Names}}'
```

如果输出里已经有 `django-study-mysql` 和 `django-study-redis`，直接跳过本节。

MySQL：

```bash
docker run -d --name django-study-mysql \
  -p 3307:3306 \
  -e MYSQL_ROOT_PASSWORD='gyc@0109' \
  -e MYSQL_DATABASE=django_study \
  -e MYSQL_USER=django \
  -e MYSQL_PASSWORD='gyc@0109' \
  -e TZ=Asia/Shanghai \
  -v django_study_mysql:/var/lib/mysql \
  --restart=no \
  mysql:8.4
```

Redis：

```bash
docker run -d --name django-study-redis \
  -p 6380:6379 \
  -v django_study_redis:/data \
  --restart=no \
  redis:8.0-alpine redis-server --requirepass 'gyc@0109' --appendonly yes
```

参数解释：

| 参数 | 含义 |
| --- | --- |
| `-p 3307:3306` | 宿主机 3307 → 容器 3306，避开本机可能已有的 MySQL |
| `-p 6380:6379` | 宿主机 6380 → 容器 6379，避开本机可能已有的 Redis |
| `-v django_study_mysql:/var/lib/mysql` | 数据存到 Docker 命名卷，删容器不丢数据 |
| `--restart=no` | **不随 Docker / 开机自动启动**（本项目的明确要求） |
| `redis-server --requirepass ... --appendonly yes` | 设密码 + 开启 AOF 持久化 |

## 六、手动启动（理解原理用）

脚本内部执行的就是下面这些命令。**每个命令都要单独开一个终端**，因为它们是长期运行的前台进程。

### 6.1 启动容器

```bash
docker start django-study-mysql django-study-redis
```

> 用 `start` 不是 `run`：容器创建过一次就一直在（`docker ps -a` 能看到），`start` 只是重新点着。`run` 是「新建并启动」，名字会冲突。

等 MySQL 真正可连（刚启动需要几秒到二十几秒）：

```bash
docker exec django-study-mysql mysqladmin -uroot -p'gyc@0109' ping
```

看到 `mysqld is alive` 才继续。Redis 验证：

```bash
docker exec django-study-redis redis-cli -a 'gyc@0109' --no-auth-warning ping
```

返回 `PONG`。

### 6.2 project1 后端（终端 1）

```bash
cd /home/gyc/Labs/Django-Study/backend
.venv/bin/python manage.py runserver 8000
```

### 6.3 project1 Celery worker（终端 2）

```bash
cd /home/gyc/Labs/Django-Study/backend
.venv/bin/celery -A config worker -l info
```

看到 `celery@xxx ready.` 才算成功。

### 6.4 project1 前端（终端 3）

```bash
cd /home/gyc/Labs/Django-Study/frontend
npm run dev
```

### 6.5 practice 三件套（终端 4、5、6）

```bash
# 终端 4：后端
cd /home/gyc/Labs/Django-Study/practice/backend
.venv/bin/python manage.py runserver 8001

# 终端 5：worker
cd /home/gyc/Labs/Django-Study/practice/backend
.venv/bin/celery -A config worker -l info

# 终端 6：前端
cd /home/gyc/Labs/Django-Study/practice/frontend
npm run dev
```

> 两个 Vite 的端口分别写死在 `vite.config.js`（5173 / 5174），同时启动不会互相抢端口。若想强制端口冲突时报错而不是偷偷换端口，可以 `npm run dev -- --strictPort`。

## 七、启动后怎么验证

### 7.1 健康检查（最有用的一条）

```bash
curl -s http://127.0.0.1:8000/api/health/
curl -s http://127.0.0.1:8001/api/health/
```

正常输出（本项目实测）：

```

```

它一次测两样东西：MySQL 能不能连、Redis 能不能读写。哪个是 `false` 就去看对应容器。

```bash
ss -ltnH | grep -E ':(8000|8001|5173|5174|3307|6380) '
```

六个端口都在监听，说明服务齐了。

### 7.3 试一个异步任务

```bash
# 1) 投递任务，拿到 task_id
curl -s -X POST http://127.0.0.1:8000/api/tasks/add/ \
  -H 'Content-Type: application/json' \
  -d '{"a": 7, "b": 35}'

# 2) 用返回的 task_id 查结果
curl -s http://127.0.0.1:8000/api/tasks/<task_id>/
```

practice 的报表任务不需要参数：

```bash
curl -s -X POST http://127.0.0.1:8001/api/tasks/report/

```

状态会从 `PENDING` → `STARTED` → `SUCCESS`。**一直 `PENDING` 就是 worker 没启动。**

## 九、停止服务与「不要开机启动」

### 9.1 一键停止

```bash
./dev.sh stop
```

它会按 Vite → Celery → Django → 容器的顺序停，并释放 8000 / 8001 / 5173 / 5174 / 3307 / 6380 六个端口。

### 9.2 这台机器的现状

本项目**已经关闭了开机自启**，依据有三条：

```bash
# 1) 两个容器的重启策略都是 no（不是 unless-stopped / always）
docker inspect -f '{{.Name}} {{.HostConfig.RestartPolicy.Name}}' \
  django-study-mysql django-study-redis
# 输出：/django-study-mysql no
#       /django-study-redis no

# 2) 没有注册成 systemd 服务
systemctl list-units --all | grep -i -E 'django|celery|vite'   # 无输出

# 3) 没有用户级 systemd 单元和 crontab 条目
systemctl --user list-units --all | grep -i -E 'django|celery|vite'   # 无输出
crontab -l 2>/dev/null | grep -i -E 'django|celery|vite'             # 无输出
```

### 9.3 如果以后又出现「开机自己起来了」

先查是谁干的：

```bash
docker inspect -f '{{.Name}} {{.HostConfig.RestartPolicy.Name}}' django-study-mysql django-study-redis
```

- 输出 `always` / `unless-stopped` → 是 Docker 策略，改回来：

  ```bash
  docker update --restart=no django-study-mysql django-study-redis
  ```

- 输出 `no` 但还是自启 → 去查 systemd（`systemctl list-unit-files | grep -i django`）或 crontab（`crontab -l`）。

> 注意：`docker start` 手动启动容器**不会**改变 restart policy。脚本也刻意不去改它。

## 十、常见故障排查

### 10.1 `./dev.sh start` 报「端口已被占用」

```bash
ss -ltnp "sport = :5173"
```

最后一列会显示 `users:(("node",pid=12345,...))`。确认是旧进程就：

```bash
kill 12345
```

再 `./dev.sh start`。

### 10.2 后端起来了，但接口 500 / 连不上数据库

```bash
curl -s http://127.0.0.1:8000/api/health/
```

如果 `db:false`：

```bash
docker ps -a --format '{{.Names}} {{.Status}}'      # 容器是不是 Exited
docker logs --tail 50 django-study-mysql            # 等它出现 ready for connections
docker exec django-study-mysql mysqladmin -uroot -p'gyc@0109' ping
```

常见原因：

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 容器刚启动就连 | MySQL 还没 init 完 | 等 20~30 秒，或 `./dev.sh start` 自动等端口 |
| `Access denied for user 'django'` | 密码/用户名和 `.env` 不一致 | 对齐 `.env` 与容器创建时的环境变量 |
| `Unknown database 'practice_db'` | 库没建 | 执行 5.5 的 `CREATE DATABASE` |
| `Can't connect to MySQL server on '127.0.0.1' (111)` | 容器没起或端口映射不是 3307 | `docker port django-study-mysql` |

### 10.3 `health` 里 `redis:false`

```bash
docker exec django-study-redis redis-cli -a 'gyc@0109' --no-auth-warning ping
```

返回 `PONG` 说明 Redis 正常，那问题在连接串——**99% 是密码里的 `@` 没写成 `%40`**，或库号写错了（project1 缓存是 1，practice 缓存是 2）。

### 10.4 任务永远 `PENDING`

`PENDING` 在 Celery 里的准确含义是「这个 task_id 在结果后端里查不到」，最常见的原因是 **worker 没启动**（任务躺在队列里没人取）。

```bash
./dev.sh status
./dev.sh logs celery
```

日志里应该有 `celery@xxx ready.`。没有就说明 worker 启动失败，往上翻报错。

### 10.5 页面能打开，但所有请求失败

- 打开浏览器开发者工具的 Network，看请求发到了哪个端口；
- 5173 的请求应该被代理到 8000，5174 的代理到 8001（见两个 `vite.config.js` 的 `server.proxy`）；
- 对应后端没启动，就会出现 `ECONNREFUSED` / 502。

### 10.6 `npm run dev` 报端口被占，然后自己换到了别的端口

Vite 默认「端口被占就顺延」。端口一变，后端 CORS 白名单（写死的 5173 / 5174）就不匹配，页面接口全挂。所以：

```bash
npm run dev -- --strictPort    # 端口被占直接报错，不偷偷换
```

`dev.sh` 里用的就是 `--strictPort`。

### 10.7 改了 `.env` 不生效

`settings.py` 是在**进程启动时**读 `.env` 的。改完必须重启对应服务：

```bash
./dev.sh restart
```

## 十一、数据存在哪

| 数据 | 位置 | 删除方式 |
| --- | --- | --- |
| MySQL 全部数据（两个库） | Docker 卷 `django_study_mysql` | `docker volume rm django_study_mysql`（**会丢数据**） |
| Redis 持久化数据 | Docker 卷 `django_study_redis` | `docker volume rm django_study_redis` |
| 日志 | `logs/*.log` | 直接删文件 |
| pid | `.run/*.pid` | `./dev.sh stop` 会自动清理 |
